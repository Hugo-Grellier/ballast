# Research: One reusable Draft PR for issue-linked feature work

Phase 0 decisions for [plan.md](plan.md). Each decision states what was chosen, why, and what was rejected. The spec left no NEEDS CLARIFICATION; these are design choices inside its requirements. Plan reviews 1 and 2 are folded into the decisions below; nothing here is deferred.

## R1. Where the checkpoint runs

- **Decision**: A new module `tools/spec_workflow/draft_pr.py`, imported by `run.py` at startup next to `ledger`, and called once from `run.py`'s `finally` block after `import_run`. Every exception it raises, including `KeyboardInterrupt`, is caught and printed there, and none of them changes `status`.
- **Rationale**: `run.py` is the only code that runs after a `ballast run` start or resume invocation ends, completed, paused or failed (FR-002). The launcher verified it before `execv`. Because the module is imported before the first agent step, the checkpoint runs code that was in memory before any agent could write to the checkout (FR-001, BL-INV-002). `tools/setup` already copies the whole `tools/spec_workflow/` directory, so the new module is installed and git-ignored with no setup change.
- **Alternatives rejected**: A step in the `ballast-feature` workflow. Spec Kit would run it as a shell step inside the run, so a failure would change the step state (violates FR-011), and it would not run when an earlier step fails. A separate `ballast pr` subcommand in `launcher.py`. It needs the operator to remember to run it, which is the problem the Issue describes (SC-002). A lazy import after the workflow. It would load a module that an agent could have rewritten during the run.

## R2. Re-checking trust before using GitHub authority

- **Decision**: Before doing anything, the checkpoint returns `skipped` (printed, no ledger event) when `BALLAST_TAMPERED` exists or the launcher's `in-progress` marker is present. It never consults files an agent could have written for anything other than data.
- **Rationale**: A tamper marker means an agent changed protected inputs during this invocation. Git configuration in a linked worktree's `.git` pointer is one of them. Running `git` or `gh` with operator credentials after that is exactly what the trust model forbids.
- **Alternatives rejected**: Recording a `failed-retryable` outcome. The run is not retryable until the operator restores the checkout and the launcher refuses the next run anyway, so a ledger state would mislead.

## R3. GitHub access through the operator's `gh`, resolved outside working trees

- **Decision**: Use the operator's authenticated GitHub CLI. `gh` and `git` are both resolved with the rule of `resolve_program` in `tools/ballast` (used by `ballast doctor`): only absolute `PATH` entries are considered; an entry inside any Git working tree is skipped, and so is a resolved executable inside one; the search continues with later entries. The checkpoint then calls the resolved **absolute paths**, never a bare `gh` or `git`.
  - `gh` absent from every `PATH` entry → `failed-retryable/gh-missing` (AC-010).
  - `gh` found only in a working tree or a relative entry → `failed-retryable/gh-untrusted`, printed as "gh not found outside working trees". No command runs.
  - `git` not found outside working trees → `failed-retryable/git-untrusted`, printed as "git not found outside working trees".
- Calls use fixed argument lists and no shell. Every call passes the repository explicitly and an environment with `GH_PROMPT_DISABLED=1`, `GH_NO_UPDATE_NOTIFIER=1`, `GH_PAGER=cat` and `NO_COLOR=1`. Each call has a 30 s limit. The full command list is in the [checkpoint contract](contracts/pr-checkpoint.md#external-commands): `gh api` reads (repository, Issue, Issue comments, pulls, compare, template contents), `gh pr create --draft` and `gh pr edit --body-file -`. Lists use `gh api --paginate --slurp`, which needs `gh` 2.48 or later.
- **Credentials kept from agents**: `run.py` removes `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` and `GITHUB_ENTERPRISE_TOKEN` from the environment it passes to the workflow engine, and therefore to every agent step. The checkpoint runs in `run.py`'s own process, whose `os.environ` is unchanged, so it still authenticates with them.
- **Rationale**: The spec's qualified environment is an authenticated `gh` (Assumptions), and `ballast doctor` already reports it. `gh` keeps credentials in its own store or the operator's environment, so Ballast never reads or handles a token (FR-013). The standard library has no GitHub client, and a hand-written HTTPS client would need to read the token itself. A `gh` or `git` found first on `PATH` inside the checkout is agent-writable; running it with operator credentials would hand the agent the launcher's authority (BL-INV-002, BL-INV-003), so the same rule `ballast doctor` applies is reused rather than a second one invented. Removing the token variables closes the path by which an operator's exported `GH_TOKEN` reached agents despite the `gh` command denial (BL-INV-003).
- **Alternatives rejected**: `shutil.which("gh")` on the plain `PATH`. A checkout-local `gh` placed by an agent would run with operator credentials; fixed arguments do not help. `urllib` with a token from the environment. Ballast would then handle the credential. A GitHub App or Action. That is an operator-side change in every project and out of scope for 1.0. Deferring token removal to a separate Issue. The checkpoint is what makes the token valuable to an agent, so the removal ships with it.

## R4. Error classification without echoing `gh` output

- **Decision**: `gh` output is never printed or stored. A failed call maps to a fixed cause: `gh-unauthenticated` (exit status 4, or HTTP 401), `gh-forbidden` (HTTP 403 or 404 on the repository itself), `github-unreachable` (timeout, or no HTTP status in the error), `github-error` (any other HTTP status). The HTTP status is read from stderr with a fixed pattern (`HTTP [0-9]{3}`). `gh-missing` and the `failed-retryable` reasons come from resolution (R3), before any call. Two refusals are recognized by fixed patterns rather than reported: a 404 on the template contents (no template, R9) and a `gh pr create` refusal containing `already exists` (cross-clone duplicate, R8). Each cause has one fixed remedy (see the [checkpoint contract](contracts/pr-checkpoint.md#causes-and-remedies)).
- **Rationale**: FR-013 and AC-014 forbid credentials in output and the ledger. `gh` does not print tokens, but relaying text Ballast does not control is the only way one could leak, and fixed messages give the single actionable remedy SC-004 asks for.
- **Alternatives rejected**: Printing `gh`'s first stderr line. It is more informative but unbounded.

## R5. Identity resolution

- **Decision**:
  - **Issue**: from the run's `feature_directory` input, matched against `specs/([1-9][0-9]{0,8})-[a-z0-9-]+`. No match → `blocked-unlinked/no-issue-number`. The Issue must exist through `gh api repos/{owner}/{repo}/issues/{n}` and must not carry `pull_request` (PRs share numbering) → otherwise `blocked-unlinked/issue-not-found` (FR-012).
  - **Local branch**: `<git> symbolic-ref --quiet --short HEAD` in the checkout. Detached → `pending/no-branch`.
  - **Branch pin (DEC-0006)**: HEAD and the upstream are agent-writable, so `run.py` records both in operator state at `ballast run start`, before the engine runs, and every checkpoint requires them unchanged. A resume never re-pins. A renamed upstream is honoured only when configured before the start.
  - **Published branch**: `<git> for-each-ref --format=%(upstream:remotename)%00%(upstream:remoteref) refs/heads/<branch>`. No upstream → `pending/not-published` (spec edge case). The published name is `remoteref` without `refs/heads/`, so a branch pushed under another name is followed.
  - **Repository**: the upstream remote's URL (`<git> remote get-url`), parsed only as `https://github.com/OWNER/NAME(.git)` or `git@github.com:OWNER/NAME(.git)` or `ssh://git@github.com/OWNER/NAME(.git)`. Anything else → `blocked-unlinked/not-github`.
  - **Pinned repository (DEC-0005)**: the upstream remote only identifies a candidate. It must equal `[github] repository` in `ballast.toml`, which `ballast trust` covers and agents cannot change; `.git/config` is agent-writable, so a remote alone would let an agent steer the operator's credentials to another repository.
  - **Base**: the repository's default branch from `gh api repos/{owner}/{repo}` (`default_branch`). A lookup failure → `failed-retryable`; there is no guessed base (spec edge case). Head equal to base → `pending/on-base-branch`.
- **Rationale**: Every value comes from Git configuration the agent sandbox cannot write (the primary `.git` is read-only to agents, a linked worktree's pointer is a trusted input) or from GitHub. Nothing is taken from agent-written text. The run does not record another base today; that belongs to the synchronization feature (Assumptions).
- **Alternatives rejected**: Letting `gh` resolve the repository from the current directory. It picks a remote by its own rules, which may differ from the branch's upstream. Deriving the branch from the feature directory name. Branch and feature names differ in practice (this feature's branch is `feat-github-draft-pr`).

## R6. "Meaningful change" through the compare API

- **Decision**: `gh api --paginate --slurp repos/{owner}/{repo}/compare/{base}...{head}?per_page=100`, every page (DEC-0008). A 404 means the head is not on GitHub → `pending/not-published`. Otherwise the change is meaningful when at least one entry of `files` has a `filename` that does not start with the prefix `FEATURE + "/"`, where `FEATURE` is the validated `feature_directory` exactly as given (for example `specs/17-draft-pr`, so the prefix is `specs/17-draft-pr/`; never `specs/` prepended again) (and, for a rename, a `previous_filename` outside it). An empty `files` list covers empty commits and changes that cancel out (AC-004). When `files` holds 300 entries (the API's cap) and none is outside the spec directory, the result is `pending/diff-unclassified`.
- **Rationale**: The three-dot compare uses the merge base and the published branch, which is exactly FR-003 ("the branch as published on GitHub"). It reads GitHub, so a stale local remote-tracking ref cannot cause a wrong decision, and it needs no `git fetch` (FR-004: observe only). Choosing `pending` when the capped list cannot be classified errs toward no PR, which an operator can override by opening one by hand (adopted per AC-007).
- **Alternatives rejected**: `git diff` against `refs/remotes/<remote>/<branch>`. It can be stale, and fetching to refresh it writes to the repository. Counting commits (`ahead_by`). Empty and self-cancelling commits would count.

## R7. Finding the feature's PR, and the decision order

- **Decision**: `gh api --paginate --slurp "repos/{owner}/{repo}/pulls?head={owner}:{branch}&state=all&per_page=100"`, with every page read, so an older closed PR is never missed. From each entry Ballast reads `number`, `state`, `draft`, `merged_at`, `base.ref`, `head.ref`, `head.repo.owner.login`, `html_url` and `body`. It keeps entries whose `head.ref` is the published branch and whose head owner is the repository owner (spec edge case on forks), and whose `html_url` is exactly `https://github.com/{owner}/{repo}/pull/{number}`. Then:
  - two or more open → `blocked-ambiguous/several-open` with every address;
  - exactly one open, with a base different from the resolved base → `blocked-ambiguous/base-mismatch`, printed as "PR #N targets X, expected Y", never `reused`;
  - exactly one open with the resolved base → `reused`;
  - none open and one or more closed or merged → `blocked-closed` with their addresses;
  - none → continue to the diff check.
  The PR lookup comes before the diff check, so a hand-opened PR is adopted even before Ballast would consider the diff meaningful.
- **Creation is verified**: after `gh pr create --draft`, Ballast lists again with the same query and records `created` only when exactly one open PR exists and its base, head and draft state match what was requested. Any mismatch → `blocked-ambiguous/create-unverified` with its address. `gh` exit 0 alone is never success (BL-INV-005).
- **Rationale**: FR-005 and AC-006 to AC-012. A human who opened a PR has already decided the work should be visible; refusing to adopt it would be surprising. A PR against another base is not the feature's PR for the resolved identity, so adopting it would falsely satisfy the issue/branch/base/PR identity. Stopping on any ambiguity creates or edits nothing (AC-011).
- **Alternatives rejected**: `gh pr list --limit 100`. It caps the result and can miss an older closed PR, then create a duplicate. Searching PR bodies for the Ballast marker. A hand-opened PR has none, and the head branch is the identity the spec names. Adopting an open PR with another base. It would record a wrong identity as `reused`.

## R8. Exclusion for concurrent checkpoints

- **Decision**: Within one clone, hold an exclusive `flock` on `<git common dir>/ballast-pr.lock` (a regular file, refused if it is a link) around "list again → create → list again". Wait at most 60 s with non-blocking retries, then report `failed-retryable/lock-busy`. Across clones, GitHub itself refuses a second open PR for the same head and base: when `gh pr create` fails with `already exists`, Ballast lists again and applies the R7 rules, so the PR the other clone created is recorded as `reused` (with the section edit), not as an error. If the list after creation shows more than one open PR, report `blocked-ambiguous`.
- **Rationale**: FR-009 and AC-009. The Git common directory is shared by every worktree of a clone, outside any worktree an agent writes, and is where the ledger already lives. No local lock can exclude another clone, so GitHub's own uniqueness rule is the cross-clone exclusion, and the list after creation catches anything that slips past both.
- **Alternatives rejected**: A per-feature lock. It adds file management for no benefit; the critical section is short. A lock held for the whole invocation. Branch-level locking is a separate roadmap item (Assumptions). Treating the `already exists` refusal as `failed-retryable`. The PR exists, so the next run would only reuse it; reusing now is the correct outcome.

## R9. PR content and the marked section

- **Decision (FR-016)**: The title is the Issue title as written, truncated to 256 characters (Assumptions). The body of a created PR is:
  1. the base branch's pull-request template, fetched with `gh api "repos/{owner}/{repo}/contents/.github/pull_request_template.md?ref={base}"` and base64-decoded. A 404 means no template, which is not an error; any other failure is `failed-retryable`. The checkout's copy is never read;
  2. a blank line, then the marked section between `<!-- ballast:draft-pr:begin -->` and `<!-- ballast:draft-pr:end -->`, holding `Related to #N`, the feature directory, the run ID, the last checkpoint time (UTC, ISO 8601) and the scope summary. The canonical text is in the [checkpoint contract](contracts/pr-checkpoint.md#pr-content).
- **Scope summary**: read from the Issue's comments (`gh api --paginate --slurp "repos/{owner}/{repo}/issues/{n}/comments?per_page=100"`). The intake scope comment is the comment whose body contains `<!-- ballast-intake:` and whose `author_association` is `OWNER`, `MEMBER` or `COLLABORATOR`; with several, the newest by `created_at`. From it Ballast copies the lines starting with `Main outcome:`, `Risk:` and `Scope gate:`, each trimmed to one line of at most 500 characters. A line that is missing is omitted. Without such a comment the summary reads "no intake scope comment". The text is inserted as plain text: `<` and `>` become `&lt;` and `&gt;` (so no HTML comment or marker can be injected) and `@` becomes `&#64;` (so no mention notifies anyone). It is never executed or passed to a shell.
- **Reuse**: only the marked section is rewritten, and only when it differs from the canonical text for this checkpoint; text outside the markers is never touched. Because the section carries the checkpoint time, a reused PR that has a section is edited at every checkpoint. When the section is absent, it is appended only if the body does not already reference the Issue (AC-007). The title, draft state, labels and reviewers are never passed to `gh pr edit` (FR-007, AC-007, AC-008). "Related to" is not a GitHub closing keyword, so merging does not close the Issue (FR-006).
- **Rationale**: Issue #17's first acceptance criterion and FR-016 require the template and a scope/status summary. Reading the template from the base branch on GitHub keeps agent-written files out of the PR (spec edge case): an agent can change the checkout's template, not the base branch's. The scope lines come from the operator-approved intake comment, and the run ID and feature path are matched against `RUN_ID_PATTERN` and `FEATURE_PATTERN` before use.
- **Security review point**: anyone who can comment on the Issue can post a comment carrying the intake marker, and the newest one wins. Escaping limits the effect to visible text in the Ballast section; restricting the author (for example to the Issue author or a repository writer) is a choice for the security review.
- **Alternatives rejected**: A body containing only the marked section (the first draft of this plan). It omits the template and scope/status summary that Issue #17 and FR-016 require. Reading the template from the checkout. An agent could write it. `Closes #N`. It would close the Issue at merge (FR-006). Rewriting the whole body on reuse. It would overwrite human text (FR-007).

## R10. Ledger recording

- **Decision**: A new ledger kind `pull_request`, source `runner`, schema version unchanged at 1. Fields: `outcome` (the FR-010 states plus `failed-retryable`), `reason?` (a fixed enumeration), `issue?` (int), `pr_number?` (int), `pr_url?` (a new `url` type restricted to `https://github.com/OWNER/NAME/pull/N`), `matches?` (int, the number of PRs for `blocked-ambiguous` and `blocked-closed`). One event per checkpoint. `report` gains a `pull_request` entry with the latest outcome, and the text report a `pull_request:` line.
- **Rationale**: The ledger accepts no free-form text, so reasons are codes and remedies (including the two base names of `base-mismatch`) are produced only in the printed line. A new kind is additive: older events stay valid and the reader still rejects unknown kinds, so a stream written by this version is not readable by an older pinned Ballast. That matches the ledger's existing forward-only rule and is stated in `ledger-schema.md`.
- **Alternatives rejected**: Bumping `schema_version`. Existing streams would need migration for an additive change. Storing PR addresses or base names as text. The schema has only scalar, validated fields.

## R11. What the checkpoint prints

- **Decision**: One line after the run summary, for example `Draft PR: created #42 https://github.com/o/r/pull/42`, `Draft PR: pending (not-published): push the branch, e.g. git push -u origin feat-x`, `Draft PR: blocked-ambiguous (base-mismatch) #7 https://…/pull/7: PR #7 targets release, expected main`, or `Draft PR: failed-retryable (gh-untrusted): gh not found outside working trees`. Any exception inside the checkpoint prints `Draft PR: failed-retryable (internal-error)` plus the exception type name, and records that outcome when the ledger is writable.
- **Rationale**: FR-010 ("`ballast run` output MUST show the latest outcome") and SC-004 (one message, one action).

## R12. Observations outside this feature's scope

- Other variables of the operator's environment still reach agents through `run.py`; only the four GitHub token variables are removed (R3). `gh`'s own credential store (`~/.config/gh` or the system keyring) is not an environment variable and stays governed by the existing sandbox rules, which this feature does not change.
- Forks: a project whose upstream remote is a fork gets a PR in that fork, not in its parent. Cross-repository PRs are out of scope.

## Plan-review decisions (agent, provisional, 2026-10-04, operator standing authority)

- A `gh` or `git` found only inside working trees maps to the spec's existing `failed-retryable` state with reason `gh-untrusted` / `git-untrusted`: fixing `PATH` and rerunning resolves it, and FR-010's outcome list stays unchanged.
- The intake scope comment counts only when its author's `author_association` is `OWNER`, `MEMBER` or `COLLABORATOR` (same rule as #27's eligibility); otherwise the summary says "no intake scope comment". Test: a marker comment from a `CONTRIBUTOR`/`NONE` author is ignored.
- `skipped` (R2) is the only outcome without a ledger event, by necessity: while `BALLAST_TAMPERED` or the `in-progress` marker exists, the ledger itself refuses every write, so the printed line is the recorded outcome for FR-010. A trust-baseline mismatch is refused earlier by the installed launcher, before `run.py` and any checkpoint run.
