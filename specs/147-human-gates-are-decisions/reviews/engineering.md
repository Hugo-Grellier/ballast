## Behavior and boundaries checked

- **Trust refresh (US1).** The global CLI asks the cached launcher for `refusal_kind` and runs `setup --refresh` only on `inputs-changed` or `pin-mismatch`, only when the pinned version declares `[setup] refresh`, and only from the verified cache or the operator's `BALLAST_STANDARD_DIR`, never the checkout. It ignores setup's exit status and then runs the unchanged launcher comparison. Setup refuses with a held lock, an unfinished attempt, or either marker. Eligibility checks these in order before any network call: a named, bound baseline repository; the current pin names the same repository, which was reviewed on this machine; every changed committed input is a regular file unchanged from `HEAD`; `.venv` and `.git` are never attributable; and every committed change equals the observed default-branch blob. Recording happens only after the regeneration and re-snapshots everything. Installed inputs must equal the installation record, committed inputs the observed blob, everything else the previous baseline, and the agent settings must equal `generated_settings`. Any doubt restores both files. `fingerprint()` includes the `ballast.toml` bytes, so an `extra_allow`-only change does force the regeneration the #141 case needs. `trust` refuses stale or malformed settings, and `launcher.STANDARD_DIR` is the pinned standard the global CLI runs, not a checkout copy. This matches D-02 option A and the two narrowings in research R2.
- **Actor rule and relays (US2).** `actor.resolve` gives `relayed` with a validated session, `operator` only when both streams are terminals, and otherwise a refusal before anything is written. `--relayed-by` is accepted only by `start`, `resume`, `continue` and `approve`. Relayed approvals are refused outside a Chat run in chat mode, both early in `run.py` (`_run_mode`) and under the run lock in `approve_many`. D-08 is enforced in `_resume_autonomous` and again in `_resume_locked` before synchronization, and in `_continue_locked`. Unknown categories fail closed. The schema refuses relayed `gate-rejection`, relayed `decision-resolution` and relayed `switch`, and requires a decision block's resolution to cite a non-default, non-approval reference. `reject`, `resolve` and `mode` stay at a terminal, and `mode` now also needs the typed `mode RUN TARGET`, which closes the human-gated-to-Chat escalation the plan's complexity table names. Every launcher command but `status` refuses under `BALLAST_AGENT_STEP`. The in-progress marker stays the boundary. Renderers (`record.md`, status, `allowed_actions`, the PR section, the ledger gate event) label relays.
- **Batch approval (US3).** Gate names are validated, ordered and de-duplicated before any read. Selection, preconditions (with earlier batch gates assumed), one typed line, a digest re-read and one atomic `append_human_decisions` all happen under one run lock. The single-gate prompt is unchanged.
- **Recovery (US4).** `discard-runs --help`/`-h` and argument refusal come before any lock, and the `Next:` line is conditional on `_trust_refusal_kind`. A postcondition at `validate-implementation` re-enters at `implement`. Exit 7 is reached only when `fallback.classify` says quota and the attempt was contained and untampered, so a dead wrapper keeps its marker. The branch offer switches only on the exact typed text at a terminal, and otherwise prints `git switch` and a shell-quoted rerun.
- **Constraints.** No new imports outside the standard library. `actor.py` is imported from the trusted installed tools. Ruff check and format pass. T043 (constitution 1.3.0) is deferred to the PR as tasks.md and the run record state.

## Concerns examined

- A relayed intent approval goes through `artifacts.record_intent`, which writes the committed `intent.md` approval block as `Approved by: human user`, sourced `ballast run approve intent`. It has no relayed label and names no session. FR-011 forbids presenting a relayed action as operator-typed in any artifact, and the PR carries `intent.md`. The run record and HD are correct, but the committed artifact is not. No test checks `intent.md` after a relayed intent approval: `AgentSessionEndToEndTests` and `test_batches_follow_the_actor_rule` relay intent but assert only status, PR body and HDs.
- In `approve_many`, `record_intent` (the operator-state registration and the `intent.md` block) runs before `_record_requirements` re-checks the later gates. If one of those raises, the run keeps a recorded intent approval with no HD. That breaks FR-007's "all or none" for that path. The earlier assumed precondition pass makes it unlikely, and the AC-019 "third precondition" case fails before `record_intent`, so this path is untested.
- When the refresh's regeneration fails, setup prints its failure and the launcher then refuses with "workflow inputs changed … run `trust`". The run does block, but the spec edge case and FR-002 ask for one combined fix. The implementer reported this deviation, and the test asserts only that a refusal exists.
- `tools/ballast` does not check `BALLAST_AGENT_STEP` before `refresh_before`. Inside a step, operator state is hidden and the marker refuses setup, so this is not a boundary gap. It is a missing defence-in-depth check, consistent with the launcher's own.
