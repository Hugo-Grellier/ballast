## What was examined

1. **Copy sources and record provenance.** Every candidate's record is read from the operator's state base keyed by the candidate's resolved path (`launcher.state_dir`, which refuses a base inside that checkout or a temp root); `read_record` requires `fingerprint == live stamp`; `_kept_record` requires shape and `mismatch` requires pin, fingerprint and an `executable` list. The copy is by content through `_open_dir`/`_copy_node` (`O_NOFOLLOW` per component on both sides, `O_EXCL` on creation, `mode & 0o755`, non-regular nodes rejected), hashed against `record.files` and `record.executable` (`copy_verified`), re-hashed by `validate` and tied to the verified record by `check_unchanged`, then verified live after the switch. `finish` writes the journal's record, which lives in operator state. Consequence: an agent that writes a sibling worktree, its own installation, or a forged `worktrees/*/gitdir` entry (SEC-007) can make a candidate be *rejected*, never make unrecorded content be *accepted*. The CLI executes only `<cache>/tools/setup` after `damage()` verifies the cache (or `BALLAST_STANDARD_DIR`, the operator's choice), under `-IS`, from a directory `trusted_standard_dir` refuses inside the checkout or a temp root. Holds.
2. **Links, hard links, special files, TOCTOU, concurrency, recovery.** `check_links(PARENTS)` before staging and for every planned path before the switch; `_linked_parent` on the source; hard links are copied by content, so a source hard link can neither leak nor inject; a FIFO or device present at a recorded path is rejected (`is not a regular file`), see SEC2-003 for the race. Locks: all `flock(LOCK_NB)`, exclusive on the new worktree, shared on each source through the copy, never created in another checkout's state (`_share`); `hold()` checks `settled` under the shared lock and retries the exclusive lock for 2 s, so two first commands end with one preparation and one `nothing to prepare` or a refusal naming the holder (AC-020). The journal is operator state, validated (`schema`, `work` regex, phase, `before`), entries pass `_safe` in `roll_back`; a committed preparation at a stale fingerprint is rolled back including `installation.json`; `trust` cannot run while a journal exists (`_hold` → `UNFINISHED`), so no baseline can be recorded over a recovered tree that was not re-verified, and that tree still meets the launcher's no-baseline refusal. Holds, with the first pass's SEC-006 residual and SEC2-002 below.
3. **Git before trust.** Five call sites in `tools/setup`, all through `GIT` (`-c core.fsmonitor=false`): `check_ignored`, `ignored`, `tracked`, `candidates` on the preparation path; `primary` and `build` only under `ballast setup`. Configuration keys traced for program execution by these subcommands: `core.fsmonitor` (disabled by `-c`, which also covers the builtin daemon), `core.hooksPath` (no hook fires for `check-ignore`, `ls-files`, `rev-parse`, `worktree list`), `alias.*` (cannot shadow builtins), `core.sshCommand`/`credential.*`/`core.askPass` (no network), `init.templateDir` (setup only; the stage's `.git` is discarded), filter and diff drivers (not used by these subcommands), `includeIf`/`safe.directory`/`core.worktree`/`core.excludesFile` (data only; a changed answer fails closed at `check_ignored` or `validate`), and `pager.<cmd>`/`core.pager`: **SEC2-001**. `tools/ballast` runs no git before the launcher on this path (`git_root` walks the filesystem; `git_output` captures output). Environment: the children inherit the operator's environment; the agent cannot set it, so no scrubbing is required against the agent.
4. **Trust baselines.** No code path in prepare mode opens any `trusted.json` (`PrepareTests.test_no_baseline_is_inherited` audit hook); the only one touched is the new worktree's own, unlinked unread before the switch (DEC-0002); `trust` and `discard-runs` refuse an uninstalled checkout before `_hold`, creating nothing (DEC-0001 excepted, SEC2-005). The launcher's no-baseline message keeps its prefix and lists only input bases that exist. Refusal texts are constants; their variable parts come from operator state (holder, record), from `REF`-validated refs, or from paths and names: **SEC2-004**. Nothing here touches #55.
5. **DEC-0001.** See SEC2-005: safe as implemented.
6. **Terminal output.** See SEC2-004.

## Findings

### SEC2-001 — high — architecture issue (contract guarantee not met)

- **Location**: `tools/setup` `check_ignored` (lines 293–312: `subprocess.run([*GIT, "check-ignore", "-q", "--no-index", path], cwd=self.root, check=False)` with inherited stdout) reached from `ballast run|ledger|intake` → `before_launcher` → `tools/setup --prepare` → `Setup.prepare` step 7, before any candidate is read and before the trust preflight. `GIT` (line 198) disables only `core.fsmonitor`.
- **Evidence**: Repository configuration `pager.check-ignore = <program>` (or `pager.check-ignore = true` with `core.pager = <program>`) makes git spawn `<program>` as the operator whenever its stdout is a terminal, which it is when the operator types `ballast run` in a shell: the CLI runs setup with inherited stdio (contract step 4) and `check_ignored` is the one git call in setup that does not capture output. Reproduced three ways: (a) git 2.53, `git -c core.fsmonitor=false check-ignore -q --no-index .ballast/x` under `script` runs the configured program, and does not without a tty; (b) a scratch test mirroring `PrepareTests.test_git_configuration_never_runs_a_program` with `pager.check-ignore` instead of `core.fsmonitor`, run under `script`, fails on the shipped code (`True is not false : pager.check-ignore ran a program before trust`) and passes with `GIT` patched to `("git", "--no-pager", "-c", "core.fsmonitor=false")`; (c) the same scratch test passes on the shipped code without a tty, which is why the first pass's regression test, run with captured stdout, cannot detect this class. The precondition is the one SEC-002 was rated high on: the repository configuration is shared by every worktree, and a linked worktree's `.git` pointer is agent-writable under the launcher's own threat model (`launcher.py` line 4: "A headless agent can rewrite anything in the checkout") and is checked only by the trust preflight, which runs after preparation. Exploit sketch: an agent in worktree A deletes A's installed entries (SEC-005a) and points A's `.git` at a gitdir it wrote with `pager.check-ignore`; the operator's next `ballast run` in A prepares and runs the program before the pointer change is reported. `ballast setup` has the same exposure through the same function (feature 14, pre-existing); this feature reaches it from the three commands operators run most.
- **Required action**: Run every git in setup with no pager and no terminal: `GIT = ("git", "--no-pager", "-c", "core.fsmonitor=false")` and `capture_output=True` in `check_ignored` (both; the flag is the guarantee, the capture removes the trigger). Regression test that gives fd 1 a pty (`pty.openpty()` + `os.dup2` around `setup.cli`, or `script`) and asserts, as `test_git_configuration_never_runs_a_program` does, that a `pager.check-ignore` program never runs during a preparation and during a `ballast setup`; without the pty the test proves nothing. Update the guarantee in [contracts/prepare.md](../contracts/prepare.md) and ADR-0011 ("git runs with `core.fsmonitor` disabled") to "git runs with no pager, `core.fsmonitor` disabled and never with a terminal on its stdout", and list the configuration keys reviewed so the next key is a conscious addition.

### SEC2-002 — low — implementation bug

- **Location**: `tools/setup` `validate` (line 922, `executables`: `st_mode & 0o111` only) and `check_unchanged` (lines 869–877: content and execute bits only).
- **Evidence**: SEC-004's fix sanitizes modes at copy time (`_copy_node`, `mode & 0o755`), but nothing re-checks modes between `copy_verified` and the switch. A process that can write the stage in that window (the first pass's SEC-006 window: an agent process surviving in the worktree being prepared) can `chmod g+w,o+w` or set-id a staged file; `validate` records it as unchanged, `check_unchanged` passes, the switch renames it in, and the installed file stays group- or world-writable for the life of the installation. The trust digests cover content, not modes, so later preflights never report it. Not exploitable from a sibling worktree (the stage is in the new worktree) and the set-id bits are moot under one UID; the write bits are the concern on a shared host.
- **Required action**: In `validate`, fail the stage when any regular file or directory under its entries has `st_mode & 0o7022` set (`validate stage modes`), the same check the copy already enforces; regression test that chmods a staged file between copy and validate, in the style of `test_stage_changed_after_verification_is_refused`.

### SEC2-003 — low — implementation bug (availability)

- **Location**: `tools/setup` `_copy_node` (lines 1362–1385): `os.stat(..., follow_symlinks=False)` decides the node type, then `os.open(leaf, O_RDONLY|O_NOFOLLOW|O_CLOEXEC, dir_fd=origin)` reads it.
- **Evidence**: The source is another worktree, where an agent may be running; a FIFO present at a recorded path is rejected by the `stat`, but a FIFO swapped in between the `stat` and the `open` blocks the open forever: the operator's `ballast run` in the new worktree hangs while holding that worktree's exclusive lock and the source's shared lock (so `ballast setup` in the source refuses as "running" until the hang is killed). Sources are walked in order, so this needs the primary and every earlier candidate to be rejected first; a symlink swap is already refused by `O_NOFOLLOW`. Related, same location: the copy runs before the digest check, so a sibling can make the copy of one path arbitrarily large (sparse file) before it is rejected; denial only.
- **Required action**: Open with `O_NONBLOCK` added, `os.fstat` the descriptor and require `S_ISREG` (and `S_ISDIR` for directories) before reading; bounding the copy size is not required (records carry digests, not sizes, and the outcome is denial only). Regression test: a FIFO at a recorded path in a sibling is rejected with `is not a regular file` and the preparation returns.

### SEC2-004 — low — implementation bug (terminal output injection)

- **Location**: `tools/setup` `fill_from_candidates` (line 851, `skipped {source}: {reason}`), `copy_candidate` (line 828, `at {differs[1]}`), `prepare` (line 477, `from {source}`).
- **Evidence**: Two agent-controlled strings reach the operator's terminal unescaped. (a) Checkout paths come from `git worktree list --porcelain -z`, which emits whatever `<common>/worktrees/<id>/gitdir` contains; reproduced with git 2.53: a gitdir file holding `/nonexistent\n\x1b[2K\rPrepared the v0.7.0 installation from /home/op/repo (verified, nothing downloaded).\n` is listed verbatim (marked `prunable`), and `candidates()` yields a prunable path with `its path no longer exists`, so `skipped` prints the forged line. Writing the common directory needs the sandbox to fail, as in SEC2-001. (b) Without any sandbox failure: a file an agent creates inside its own worktree's installation (for example `.ballast/spec_workflow/<name with \n and escapes>`) is copied by name into the stage, becomes the first differing key, and is printed in `skipped <sibling>: its content differs from its record at <name>`. Impact is limited to the operator's screen: exit statuses, the journal and the launcher's stderr refusal are unaffected, and preparation already rejected the source; but a cleared line followed by a forged `Prepared …` or `setup: refusing: …` sentence is exactly the forgery the focus asks to exclude.
- **Required action**: Escape control and non-printable characters in every path or name setup prints (`tools/ballast` has `printable()`; setup needs the same three-line helper applied in the three locations above); regression test with a sibling file name containing `\n` and `\x1b` asserting the printed line is one line of printable text.

### SEC2-005 — info — DEC-0001 verified

- **Location**: `tools/spec_workflow/launcher.py` `main` (`stranded`, lines 416–426), `_marked`, `_discard`.
- **Evidence**: The exception fires only when `state_dir(root)/in-progress` exists, which only the operator-side wrapper writes in operator state; `_discard` stops a `SCOPE`-validated unit through `systemctl`, removes `RUN_STATE` with `_remove_tree` (`O_NOFOLLOW` per component) and unlinks the marker; nothing from the checkout is executed, and `trust` keeps refusing. One wording gap: contract [cli-and-launcher.md](../contracts/cli-and-launcher.md) says no state file is created on an uninstalled checkout, but the stranded path goes through `_hold`, which opens `checkout.lock` in the (already existing) state directory. Also verified that the DEC-0001 circle is closed with a journal present: `_hold` refuses `UNFINISHED`, `ballast setup` recovers the journal first and only then refuses on the marker, after which `discard-runs` proceeds.
- **Required action**: None in code; note the `checkout.lock` exception in the contract sentence.

### SEC2-006 — info — threat-model note for the merge review

- **Location**: `research.md` R4 ("Git's worktree metadata lives in the common directory, which the agent sandbox keeps read-only"), `launcher.input_bases` docstring, versus `launcher.py` line 4.
- **Evidence**: Every git-configuration vector on the preparation path (SEC-002, SEC2-001, and any key added to git later) is reachable only through the common directory or a redirected pointer, so its severity rests on the agent sandbox: Codex `workspace-write` keeps `.git` read-only; Claude runs with `acceptEdits`, `Edit(./.git/**)` denied and no `Bash(git config …)` allow. The feature's documents state both that the sandbox holds and that an agent can rewrite anything in the checkout. The launcher treats the pointer as a protected input precisely because the second statement is the design assumption; preparation should be held to the same assumption, which SEC2-001's belt-and-braces fix does.
- **Required action**: None beyond SEC2-001; the merge review may want R4's sentence to say "even if the sandbox fails" rather than rely on it.

## Not found (negative results worth recording)

- No path by which copied content can differ from an operator-state record (focus 1), including through the own kept copy, a forged worktree list, a sibling the agent writes, a redirected `XDG_STATE_HOME`, hard links, or a recovered committed journal.
- No trust baseline is created, copied, consulted or left in place across worktrees (focus 4); `trust` cannot run on an uninstalled checkout or while a journal exists.
- No network call and no execution of anything from a checkout on the preparation path; the Python children run under `-IS` from the verified cache.
- Concurrency: no lock-ordering deadlock (all non-blocking), one preparation per worktree, no state file created in another checkout.
