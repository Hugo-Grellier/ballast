# Research: Branch Synchronization Before Agent Steps

Phase 0 decisions for [plan.md](plan.md). Each decision states what was chosen, why, and what was rejected. The spec leaves no NEEDS CLARIFICATION. DEC-0001 to DEC-0004 in [decisions.md](decisions.md) are resolved by the operator, and every finding of [plan review 1](reviews/plan-review-fable-1.md) is accepted. DEC-0005 (option A) and DEC-0006 (option B) are resolved, and every finding of [plan review 2](reviews/plan-review-fable-2.md) (N-01 to N-12) is accepted; revision 3 applies them. Revision 4 applies [plan review 3](reviews/plan-review-fable-3.md) (P-01 to P-06) and DEC-0007 option B (partial clones refused). Each changed decision names the finding it answers.

## R1. Where the check runs

- **Decision**: A new trusted module `tools/spec_workflow/branch_sync.py`, imported by `run.py` at startup next to `draft_pr` and `autonomy`. `run.py` calls `branch_sync.synchronize(root, run_id, ...)` once per `start`, `resume` and `continue` invocation, in the following order:
  - Human-gated `start` and `resume`: after argument validation, the tamper check, the Autonomous-resume refusal and the `specify` lookup, and before `_launch`.
  - Autonomous `start`: after eligibility and `autonomy.write_run`, before `_launch` (R10).
  - `continue`: after argument and source-run validation, and before the human decision is recorded and the source run is lowered. The new run ID is drawn before the check. A non-blocked check records its event and writes the continuation's pin under the new ID. A blocked check records its event under the source run, whose archive already exists, and writes no pin, so a blocked or retried continuation leaves no phantom run archive and changes no other record (N-07).
  - `publish` does not run the check. It starts no agent step (FR-001).
- **Rationale**: The launcher has already verified the trusted inputs before it executes `run.py` (`launcher._refusal`), and no agent has run yet in this invocation. The module is in memory before any agent can write to the checkout, so it satisfies FR-001, FR-012 and AC-017 the same way `draft_pr` does (#17 research R1). `tools/setup` already copies the whole `tools/spec_workflow/` directory, so the new module needs no setup change.
- **Alternatives rejected**:
  - A shell step at the top of each workflow. An agent-visible engine step could be skipped by a resume that starts after it, and its failure would read as a step failure, not a launcher block.
  - A check in `launcher.py` before `execv`. The launcher would then need the run's identity, the ledger and the Autonomous record, which belong to `run.py`. Keeping `launcher.py` small keeps the trust check easy to review.

## R2. Rebase without running the checkout's Git configuration

- **Decision**: The rebase is not `git rebase` in the checkout. Every network or merge operation runs in a throwaway bare repository under the operator state directory (R3a). That repository has an empty configuration, so only the operator's global and system configuration apply. The replay, for each commit `C` of `git rev-list --reverse --topo-order --no-merges OLD_BASE..HEAD`, is:
  1. `[git, "--attr-source=" + NEW_BASE, *GIT_HARDENING, *NO_MAINTENANCE, "merge-tree", "--write-tree", "--merge-base=" + C^, "--name-only", "-z", PARENT, C]` (F-05, N-02). `--attr-source` is a global `git` option and goes before the subcommand: placed after `merge-tree` it is rejected with exit 129 (reproduced in review 2). Exit 1 is a conflict. The conflicting paths come from the `--name-only -z` output.
  2. If the resulting tree equals `PARENT^{tree}` and `C` was not empty, the commit is dropped, as `git rebase` drops a change already upstream.
  3. Otherwise the new commit object is the original commit's raw text (`git cat-file commit C`) with `tree` and `parent` replaced, `gpgsig` headers removed and a fresh `committer` line. The result is written with `git hash-object -t commit -w --stdin`, which validates the object. Author, encoding and message are kept byte-for-byte.

  The committer line is `git var GIT_COMMITTER_IDENT`, run **in the throwaway repository** (F-12). Its empty local configuration means the identity comes from the operator's environment and global or system configuration, never from the checkout's agent-writable `.git/config`. If Git reports no identity, the check blocks as `internal-error` with the detail "no committer identity" and the recovery to set `user.name` and `user.email` in the operator's global configuration.

- **Attributes** (F-05): `git --attr-source=NEW_BASE` makes `merge-tree` read `.gitattributes` from the fetched base tree. Without it, a bare repository reads none, so `merge=union`, `merge=ours`, `binary` and `text`/`eol` would differ from `git rebase` and a union-merged changelog would block as `conflict`. Attributes come from the operator's base branch, so an agent's `.gitattributes` on the feature branch is never consulted. A merge driver still runs only when the operator's global configuration defines it. The remaining differences from `git rebase` are: replayed commits are unsigned, attributes come from the base and not from each replayed commit, and no `rebase.*` configuration applies. ADR-0005 and the policy section state them.
- **Rationale**: The checkout's `.git/config`, `.gitattributes` and hooks are agent-writable (#17 DEC-0004/0005). `git rebase` there would run merge drivers, `gpg.program`, `core.sshCommand` and hooks with operator authority (FR-012). `merge-tree --write-tree` never touches the index or working tree. A conflict therefore changes nothing: "abort and return to the previous HEAD" (AC-007) holds by construction, not by cleanup, and Ctrl-C mid-replay leaves no rebase in progress (edge case "interrupted synchronization"). Merge commits on the feature branch are dropped and their non-merge commits replayed, which is what `git rebase` does by default (A-1). A base that requires signed commits rejects the push, which reports `push-failed`, not retryable. The review's experiment replayed a four-commit history and got the same kept and dropped commits, and the same IDs at equal timestamps, as `git rebase`.
- **Requirement**: `merge-tree --merge-base` needs Git 2.40 and the global `--attr-source` option Git 2.41, so the floor is **Git 2.41** (N-02). An older or untrusted `git` blocks the check as `git-unavailable` (DEC-0001), and `ballast doctor` reports the same floor.
- **Alternatives rejected**:
  - `git rebase` in the checkout with `-c` overrides. No override list covers every program-running key (#17 DEC-0004 reached the same conclusion for push).
  - `git rebase` in a throwaway with a full working tree. It writes every file of the repository to disk on each check.
  - `git replay`. It is still marked experimental in Git.
  - A temporary `git worktree add`. It writes the checkout's worktree list and still reads its configuration.

## R3. Fetch, published branch and default branch

- **Decision**: The fetch URL is `https://github.com/OWNER/NAME.git` or `ssh://git@github.com/OWNER/NAME.git` for the repository pinned under `[github] repository` in the protected `ballast.toml`. The scheme follows `origin` (`autonomy._push_url`); the repository never comes from the remote. With no pin, the cause is `unknown-base` (A-6). In the throwaway repository:
  1. `git ls-remote --symref URL HEAD refs/heads/BASE refs/heads/BRANCH` (30 s), once per invocation. It returns the default branch, the base commit, and whether and where the branch is published. When the pin has no `base` yet (a fresh `start`, or a pin #17 wrote), the call is `git ls-remote --symref URL HEAD refs/heads/BRANCH`: the `HEAD` symref names the default branch, which becomes the base, and the `HEAD` line of the same advertisement is its commit, so no second call is needed. The pin's `base` is written only after this call succeeded; a failed call leaves a pin with `branch` only, and the next invocation fills `base` the same way (N-06, R12).
  2. When the base or published commit is missing locally, `git fetch --no-tags --no-write-fetch-head URL +refs/heads/BASE:refs/sync/base [+refs/heads/BRANCH:refs/sync/published]` (600 s). The throwaway first gets `refs/haves/*` pointing at the local HEAD and the pin's `base_commit`, so negotiation sends only missing objects. When both commits are local, there is no fetch (SC-005). "Missing locally" is probed with `cat-file -e` **in the throwaway repository**, under `GIT_NO_LAZY_FETCH=1`: it reads the shared object store and has no promisor remote, so the probe can never fetch through the checkout's `origin` (N-04).
  3. The observed base and published commits are the `ls-remote` values, replaced by the fetched ref values when a fetch ran. The observed published commit is the push lease (R5).

  A non-zero exit or timeout of either command is `fetch-failed`. A missing base ref, an empty repository, or a recorded base that no longer exists is `unknown-base`. The default branch is never substituted for a recorded base. The pin's `base_commit` is used only as the old base (R8) and as a negotiation hint, never as the current base (FR-003). The local remote-tracking refs (`refs/remotes/*`) are neither read nor written.
- **Why `ls-remote` stays on every invocation** (F-14): it is the only call that tells "branch not published" apart from a failure without a fetch error, and the default branch it returns is needed every time by the feature-branch rule (R15), not only when the pin lacks a base. It also lets the fetch be skipped entirely when the objects are local. An up-to-date check therefore costs one `ls-remote` and usually no fetch.
- **Rationale**: `ls-remote --symref` gives the default branch without `gh`, so synchronization needs no GitHub API call and no token. Reading the published branch from GitHub, not from `refs/remotes/origin/*`, means a stale or agent-written tracking ref cannot hide a push (AC-013).
- **Alternatives rejected**:
  - `gh repo view` for the default branch, as `autonomy.repository` does. It adds a `gh` dependency and an API call for a value Git returns itself.
  - Fetching through `origin`. Its URL, `pushurl`, `insteadOf` and `sshCommand` are agent-writable.

## R3a. The throwaway repository and object sharing

- **Decision** (F-01, F-09, F-11): `branch_sync` creates its own throwaway repository; `autonomy._push` is not changed and keeps `objects/info/alternates`.
  - Creation: `git init --quiet --bare --template= --object-format=FORMAT DIR` under `<state_dir>`, in a fresh `tempfile.TemporaryDirectory`, deleted afterwards. `FORMAT` is `git rev-parse --show-object-format` read in the checkout and accepted only as `sha1` or `sha256` (F-09). `--template=` (empty) copies no hooks or files from the operator's `init.templateDir` (F-11).
  - Object sharing: every command in the throwaway runs with `GIT_OBJECT_DIRECTORY=<checkout common dir>/objects`. Fetched objects and replayed commits land directly in the checkout's object store, where the local update needs them. The throwaway's own `objects/` stays empty.
  - Garbage collection: every command in the throwaway runs with `NO_MAINTENANCE = ("-c", "maintenance.auto=false", "-c", "gc.auto=0", "-c", "fetch.writeCommitGraph=false")` after `GIT_HARDENING`. The throwaway runner is the only way `branch_sync` runs Git there, and it always adds both tuples, so no call can forget them.
  - Environment: the `_push` environment (Git location and `GIT_CONFIG_*` variables dropped, filtered `PATH`), plus `GIT_TERMINAL_PROMPT=0`, `GIT_NO_LAZY_FETCH=1`, and no askpass program (N-09): `GIT_ASKPASS` set to the empty string (Git then skips `core.askPass` and `SSH_ASKPASS` and falls to the disabled terminal prompt), `SSH_ASKPASS` removed, `SSH_ASKPASS_REQUIRE=never` (OpenSSH 8.4 and later), and `DISPLAY` and `WAYLAND_DISPLAY` removed so an older `ssh` has no graphical askpass to fall back to. Network commands run with `stdin=DEVNULL` and `start_new_session=True`, so neither Git nor `ssh` can open the terminal for a prompt (F-11). A prompt that cannot be answered fails the command at once, which classifies as `fetch-failed` or `push-failed` with the existing recovery.
  - Checkout-side commands (R5, R6 and the classification steps) also run with `GIT_NO_LAZY_FETCH=1`. Partial clones are refused (below), so this is defense in depth: should a promisor configuration appear after the shape check, a missing object fails the command instead of being fetched through the agent-writable `origin` (N-04, DEC-0007).
- **Partial and shallow checkouts** (N-04, N-12, DEC-0007 option B): R4 step 2 reads, as data, `rev-parse --is-shallow-repository` and the checkout's `extensions.partialClone`, `remote.*.promisor` and `remote.*.partialclonefilter` values (`git config --get` / `--get-regexp`, which run no program).
  - Shallow: blocks as `git-unavailable` with the detail "shallow checkout" and the recovery "git fetch --unshallow, then rerun". `.git/shallow` grafts answer `merge-base` differently from the throwaway and would make negotiation promise objects the checkout lacks.
  - Partial clone (any of the three keys set, whatever the Git version): blocks as `git-unavailable` with the detail "partial clone" and the recovery "clone the repository again without --filter, then rerun". One action (SC-003). The in-place conversion is not printed: review 3 reproduced that `git fetch --refetch origin` re-applies the filter, and that `git fetch --refetch --no-filter origin` fetches every object but leaves `remote.origin.promisor` and `remote.origin.partialclonefilter` set (and `extensions.partialClone` on older clones), so it takes three or four commands and the shape check would still refuse after the first.
  - `GIT_NO_LAZY_FETCH=1` stays on every command, in the throwaway and in the checkout, as defense in depth.
- **Later extension: partial-clone support** (not in this feature; DEC-0007 option A, recorded so it is not re-derived): Git 2.46 or later (`GIT_NO_LAZY_FETCH` is ignored before it) as a second floor; before any mutation, every blob `diff-tree -r OLD NEW` writes is checked present with `cat-file --batch-check` in the throwaway, after dropping null OIDs (deleted paths), which `--batch-check` otherwise reports as missing; a missing blob blocks before the push; the recovery is the three-command conversion above, not `--refetch` alone. Its test needs a stand-in remote with `uploadpack.allowFilter` (otherwise the clone is silently full) and a `--sparse` variant, because whether the throwaway fetch supplies a blob the checkout lacks depends on the server's sparse walk (`pack.useSparse`), which GitHub's behavior cannot be shown to match offline.
- **Why gc cannot reach the checkout's objects**: in a repository whose object directory is the checkout's, a `gc`, `repack` or `prune` would use the throwaway's few `refs/sync/*` and `refs/haves/*` as the only roots and delete every other branch's loose objects (reproduced in the review). Three things rule that out:
  1. No command in the throwaway is `gc`, `repack`, `prune`, `maintenance` or `fsck`. The contract lists the allowed commands.
  2. The one listed command that starts maintenance on its own is `fetch` (`maintenance run --auto` or `gc --auto` at the end). `maintenance.auto=false` and `gc.auto=0` turn that off. Command-line `-c` values take precedence over the operator's global and system configuration, so a global `gc.auto=1` cannot turn it back on.
  3. `fetch.writeCommitGraph=false` keeps `fetch` from writing a commit-graph for the checkout from the throwaway's refs.

  `push`, `merge-tree`, `hash-object`, `update-ref`, `cat-file` (including `-e`), `ls-remote`, `rev-parse` and `var` start no maintenance.
- **Rationale**: Alternates, as `_push` uses, would put fetched objects in the throwaway, which is deleted, so the checkout could not use them. `GIT_OBJECT_DIRECTORY` is the simplest way to fetch into the checkout without reading its configuration; the price is the gc exposure, closed above and covered by a regression test (quickstart scenario 37).
- **Alternatives rejected**:
  - Moving `_push` onto a shared helper. It would change `_push` from alternates to `GIT_OBJECT_DIRECTORY`, which is not "behavior unchanged" (review, scope note). `branch_sync` reuses only `draft_pr._resolve`, `draft_pr._child_path`, `draft_pr.GIT_LOCATION` and `autonomy.GIT_HARDENING`.
  - Copying fetched objects from the throwaway into the checkout afterwards. It needs a second object transfer and a second place to get wrong.

## R4. Classification order

- **Decision**: One pass, stopping at the first block:
  1. Take the lock (R7). Busy → `busy`.
  2. Resolve `git` outside working trees and check its version (2.41 or later), then the checkout's shape: shallow, or a partial clone (R3a) → `git-unavailable` (DEC-0001, N-02, N-12, DEC-0007).
  3. Operation in progress (`rebase-merge`, `rebase-apply`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `BISECT_LOG` under `git rev-parse --git-path`) → `in-progress`. An `index.lock` present (`rev-parse --git-path index.lock`) is also `in-progress`, with the detail "another git process may hold the index ({path} exists)" and the recovery "if no git process is running, remove {path}, then rerun" (P-03). It is checked here, before anything runs `read-tree`: with a stale lock `status`, `diff-index` and `update-ref` still succeed but `read-tree` and `read-tree --dry-run` exit 128, which step 13 would otherwise misreport as `dirty`.
  4. Identity (R12): read the pin. `start` with no pin writes `{branch}` with the current branch; `base` is added in step 5. `resume` or `continue` whose run (for `continue`, the source run) has no branch pin → `wrong-branch` with the recovery to start a new run (DEC-0006). Detached HEAD, or a branch other than the pinned branch → `wrong-branch`.
  5. `ls-remote` and fetch (R3) → `unknown-base` or `fetch-failed`. A pin without `base` gets it now (N-06).
  6. Pending write-ahead record for this branch (R5, `<state_dir>/branch-sync/<key>.json`, whatever run wrote it) → complete the half-done sync, or clear the record (N-01).
  7. Branch kind (R15): feature branch, base branch, or other.
  8. Published branch: local equal to or ahead of published → continue. Local strictly behind published: clean → fast-forward to it (AC-015) with the local update of R5; dirty → no fast-forward, continue (F-13). Both have commits the other lacks → `diverged`.
  9. Base commit an ancestor of HEAD → `up-to-date` (FR-004), unless HEAD changed in step 6 or 8, then step 14. The checkout is not inspected for dirt: an up-to-date branch with work in progress is normal.
  10. Behind, and not a feature branch: the base branch is fast-forwarded when HEAD is an ancestor of the base, otherwise `diverged` (DEC-0003); any other branch → `not-feature-branch` (DEC-0004). The base-branch fast-forward is a mutation like any other and goes through R5, whose step 1 checks the tree first, so a dirty base branch blocks as `dirty` and no uncommitted change is carried across a `read-tree` (N-10).
  11. Dirty → `dirty` (R6).
  12. Old base chosen (R8). When HEAD has no commits beyond the old base, the new HEAD is the base commit (fast-forward). Otherwise replay (R2) → `conflict`, or `diverged` when the base was rewritten and the old base is unknown.
  13. Pre-mutation checks, then write-ahead record, push and local update (R5) → `dirty`, `busy`, `diverged` or `push-failed`.
  14. Protected-input recheck (R9) whenever HEAD changed in this invocation → `protected-input`.
  15. Overlap with plan and review evidence (R11). It is recorded and never blocks.
- **Every fast-forward is an R5 mutation** (N-10): the AC-015 fast-forward (step 8), the base-branch fast-forward (step 10), a fast-forward with no feature commits (step 12) and a record completion (step 6) all go through R5 steps 1 (pre-mutation checks, including "still clean"), 2 (write-ahead record), 4 (local update) and 5 (completion). Step 3, the push, runs only for a published feature branch, and only when `NEW != OBSERVED` (P-01): the AC-015 fast-forward never pushes, so its record has `published_old == new_head`, and the base-branch fast-forward records `published_old` null.
- **Rationale**: Every step before 13, other than the fast-forwards above, only reads or writes new, unreferenced objects (and, in steps 4 and 5, the operator-side pin). A block in steps 1–12 therefore leaves HEAD, index, working tree and the published branch unchanged (SC-002); a fast-forward blocked by its own R5 checks has changed nothing yet. The cheap local checks run before the network call, so a wrong checkout fails fast. Step 14 is the last step before any non-blocked outcome, so no path that moved HEAD can skip it (F-02).
- **AC-015 with a dirty tree** (F-13): when the local branch is strictly behind its published branch and the tree is dirty, the fast-forward is skipped and the check continues with the local HEAD. If the base is already in HEAD, the outcome is `up-to-date` and the printed line adds "published branch is ahead; not fast-forwarded: uncommitted changes". If the base is not in HEAD, step 11 blocks as `dirty`. A replay and push cannot happen while the local branch lacks published commits: a clean tree would have fast-forwarded in step 8 first, and a dirty one blocks in step 11.

## R5. Updating the published and local branch

- **Decision**: Check everything that can be checked locally, write a write-ahead record, push, then update locally (F-03). Every mutation goes through these steps, including each fast-forward (R4, N-10); only the push is limited to a published feature branch.
  1. **Pre-mutation checks**, under the lock, before anything is pushed or moved:
     - HEAD still `OLD` (otherwise `busy`) and the tree still clean (R6). A dirty tree blocks as `dirty` here, also for the base-branch and AC-015 fast-forwards (N-10).
     - Ignored files: `diff-tree -r --name-only --no-renames -z OLD NEW` intersected with the ignored paths from `status --porcelain=v1 -z --ignored=matching --untracked-files=all`. A non-empty intersection blocks as `dirty` with the detail "ignored files would be overwritten: {paths}" (F-07). `read-tree` would overwrite such a file, and a restore would delete it.
     - `git read-tree -m -u --dry-run OLD NEW`. A failure here is `dirty` with the paths Git refused (untracked files in the way).
     - The protected-input diff (R9): its names are known now, before any mutation (F-02).
  2. **Write-ahead record** (N-01): `{"branch": BRANCH, "old_head": OLD, "new_head": NEW, "published_old": OBSERVED or null, "run_id": RUN, "written_at": TIME}` is written to `<state_dir>/branch-sync/<key>.json`, next to the lock and under the same key (`sha256(branch)[:16]`, R7), mode `0600` in a `0700` directory, replaced atomically. It is keyed by branch, not by run, so the next invocation on the branch finds it whatever its run ID: a `resume`, a `continue` (new continuation ID), the Autonomous restart `start --mode autonomous` (new run ID) or a new human-gated `start`. It is written for every mutation, published or not. A failed write is `internal-error` and nothing has changed. `published_old` non-null and different from `new_head` is the record's marker for "this mutation pushes" (P-01): it is non-null only for a published branch, and equal to `new_head` exactly when step 3 is skipped.
  3. **Push** (published feature branches only, and skipped when `NEW == OBSERVED`, P-01): from the throwaway repository, `git push --force-with-lease=refs/heads/BRANCH:OBSERVED URL NEW:refs/heads/BRANCH`, where `OBSERVED` is the observed published commit. A lease rejection (`stale info`, or a rejection that names the ref as changed) is `diverged`. Any other failure is `push-failed`, with `retryable` set for a timeout or transport error and cleared for a remote rejection (protected branch, required signatures, hook declined) (AC-014). The record is kept: a timed-out push may have landed, and the next invocation finds out from the published commit. An unpublished branch is never pushed. The base branch and any branch that is not a feature branch are never push targets (DEC-0003, DEC-0004).
  4. **Local update**: in the checkout, with `autonomy.GIT_HARDENING`, `filter_overrides` and `GIT_NO_LAZY_FETCH=1`:
     1. `git read-tree -m -u OLD NEW` updates the index and working tree.
     2. `git update-ref -m "ballast: sync onto BASE" refs/heads/BRANCH NEW OLD` moves the branch, but only if it still points at `OLD`.

     If step 2 fails, something outside Ballast moved the branch during the check, and the cause is `busy`; the record is kept. A lost CAS means HEAD is now some `X != OLD`, so the restore targets the current HEAD's tree, not `OLD` (P-04): `read-tree -m -u NEW HEAD`, run only while the index and working tree still hold nothing but the sync's output (`diff-index --cached --quiet NEW`, `diff-files --quiet`); otherwise they hold someone else's work and are left as they are. The rule: after a lost CAS, when the index and worktree hold only the sync's output, make them match whatever HEAD now is. When the operator committed the staged tree (`X^{tree} == NEW^{tree}`) the restore is a no-op and the tree is clean against `X`; the next invocation reaches row 5.
  5. **Completion**: set the pin's `base_commit` (R12), then delete the record. A crash between the two leaves a record whose state matches the first row of the recovery table, which clears it.
- **Recovery state machine** (step 6 of R4). With a pending record for the current branch `{old_head, new_head, published_old, run_id}`, local HEAD `L` and observed published commit `P` (absent when unpublished):
  - A record file that exists but fails validation (R12 types, `branch` not the current branch) is `internal-error` with the detail "invalid write-ahead record" and is kept: the file is operator-only, so an invalid one is a Ballast defect, and clearing it silently could hide a push that landed (N-11).
  - First, `cat-file -e new_head` in the throwaway (N-04, N-11). For an unpublished branch, `new_head` is unreferenced until `update-ref`, and the checkout's own gc can delete it. When it is missing and `P != new_head`, the row is "anything else".
  - The rows are evaluated top to bottom; the first match applies. "The record records a push" means `published_old` is non-null and `published_old != new_head` (R5 step 2).

  | # | Observed state | Meaning | Action |
  | --- | --- | --- | --- |
  | 1 | `L == new_head`, and `P == new_head` or `published_old` is null | finished, record not cleared | clear the record, continue the check |
  | 2 | `L == new_head`, `P == published_old`, and the record records a push (P-01) | local moved, push missing (not reachable with push-first; cheap to cover) | push with lease `published_old`, then clear |
  | 3 | `L == old_head` and `diff-index --cached --quiet new_head`; nothing else (P-02) | interrupted between `read-tree` and `update-ref` | `update-ref` with CAS `old_head`, then clear; `recovered` true; then R4 step 14 |
  | 3b | `L == old_head`, `diff-index --cached --quiet old_head`, at least one `status` entry, and every entry, untracked ones included, is a path of `diff-tree -r old_head new_head` whose content equals `new_head`'s: `hash-object --no-filters PATH` equals the blob `ls-tree new_head -- PATH` names, or the file is absent where `new_head` deletes it (P-03) | interrupted during `read-tree -m -u`: the index is still `old_head`, part of the worktree is already `new_head` | block `dirty` with the detail "an interrupted update left these files at the synchronized content: {paths}" and the one recovery "git restore --source={new_head} --staged --worktree ., then rerun to finish the synchronization"; the record is kept. After that command the index and worktree equal `new_head` and the rerun lands in row 3 |
  | 4 | `L == old_head`, `P == new_head` | push done, local not | R5 steps 1, 4 and 5 for `old_head..new_head`; `synchronized` with `recovered` true |
  | 5 | `L != old_head` and `L` descends from `old_head`, `P == new_head`, and the record records a push (N-03, P-01) | push done, then someone committed on the old local branch: the completion was blocked `dirty` and the operator committed, or a commit landed between the push and the CAS (`busy`) | replay `old_head..L` onto `new_head` with the R2 machinery (old base `old_head`, new base `new_head`), then R5 steps 1–5 with `OLD = L`, the replay result as `NEW` and the lease `new_head` (no push when every replayed commit is dropped, since `NEW == OBSERVED`); the new record replaces the old one; `synchronized` with `recovered` true |
  | 6 | `L == old_head`, `P == published_old` or `published_old` null | nothing landed | clear the record, continue the check from the start |
  | 7 | anything else | someone else changed a branch | clear the record, continue the check; it classifies the state as usual |

  **Invariant** (P-01): no recovery row pushes unless the record records a push; a fast-forward record (AC-015, base branch, no feature commits) never does. A fast-forward record whose local branch gained commits therefore falls to row 7, and the normal classification reports `diverged` with `git pull --rebase`, the same as without the crash. The branch kind (R15) is decided after the table, so the record itself, not the kind, carries this.

  Row 1 clears the record without a HEAD change in this invocation, so R4 step 14 does not run for the HEAD change the crashed invocation made (point H: after `update-ref`, before the record delete). That recheck is not lost: `launcher._refusal` compares the protected inputs with `trusted.json` before `run.py` executes at all, so a protected change brought in by the crashed sync refuses the rerun before the check runs (P-05).

  Row 3 needs no worktree or untracked-file test: `read-tree -m -u` writes the index last, so an index equal to `new_head` proves the worktree update completed, and `update-ref` touches no file. An operator edit or untracked file made since the crash survives the CAS unchanged, and is the operator's own state afterwards (P-02). Row 3 also has no condition on `P`: when the published branch moved on after Ballast's push, finishing the local update first and classifying `L == new_head` against the new `P` is better than leaving a staged tree.

  Row 3b is the one interruption point that needs a printed command (DEC-0005 still holds: one action, then rerun). `read-tree -m -u OLD NEW` cannot resume by itself ("not uptodate"), and staging the paths automatically would add a primitive to the checkout-side list, so the row stays read-only. Any `status` entry that fails the content test is the operator's, and the row does not match: the state falls to row 4 or 6 and the existing `dirty` advice. A stale `index.lock` left by a SIGKILL is reported first, as `in-progress` at R4 step 3; once it is removed, the rerun reaches row 3b. Ctrl-C removes the lock itself and reaches row 3b at once.

  Row 3 comes before row 4 so that a published branch interrupted between `read-tree` and `update-ref` is completed by the CAS, not refused as dirty by row 4's pre-mutation checks.

  A completion that moved HEAD goes through the protected-input recheck (R9) like any other. A completion blocked by its own checks keeps the record and reports that cause with the post-push detail below. A conflict in row 5 is `conflict` with the recovery "git rebase --onto {new_head} {old_head} {branch}, resolve, then rerun"; after that manual rebase the branch descends from `new_head`, row 7 clears the record, and the normal classification sees a local branch ahead of its published branch. The `recovered` ledger event names the run that wrote the record (`recovered_from`).
- **A block after a successful push** (DEC-0005, option A): a failure after the push (the local update's CAS lost, `read-tree` failing despite the dry run, Ctrl-C, a crash, a completion blocked by its own checks) leaves the published branch at `NEW` while the outcome is blocked. Spec SC-002 makes this its second exception. The next invocation completes the synchronization from the branch-keyed record; nothing pushes the old commit back. The block's detail adds "the published branch already holds {new_head}" and its recovery is "rerun to finish the synchronization", so SC-003 still gives one action. A completion blocked as `dirty` instead says "a previous synchronization already pushed {new_head}; " followed by the step-1 detail ("uncommitted changes: {paths}", "ignored files would be overwritten: {paths}" or "untracked files are in the way: {paths}", P-06), with the recovery "move these changes aside without committing them (Ballast never stashes or discards them), then rerun to finish the synchronization" for uncommitted changes and "move or commit these files, then rerun to finish the synchronization" for ignored or untracked files, so the advice for uncommitted changes does not lead into row 5; row 5 still handles an operator who commits anyway (N-03). Row 3b's interrupted `read-tree` is the one post-push state whose recovery is a specific command (`git restore --source={new_head} --staged --worktree .`), because its dirty paths are the sync's own output (P-03).
- **Rationale**: Pushing before touching the checkout means a rejected push needs no local restore at all (FR-007, AC-014). The pre-mutation checks move every common local refusal before the push. After a replay, `NEW` does not descend from `OLD`, so a half-done sync would otherwise look like `diverged` and need a manual merge; the write-ahead record lets the next invocation finish it with no manual step, whatever its run ID. Plumbing commands run no `post-checkout` or `post-rewrite` hook, and the hooks path is `/dev/null` anyway.
- **Alternatives rejected**:
  - Local update first, then push, then reset on failure. A crash between the two steps would leave a rewritten local branch that its published branch has diverged from.
  - `git reset --keep`. It cannot compare-and-swap the ref.
  - The record in the per-run pin (revision 2). A restart, a continuation or a new `start` gets a new run ID and never sees it (N-01).
  - A lease push back to `published_old` before reporting a post-push block (DEC-0005 option B, not chosen).

## R6. What "dirty" means

- **Decision**: `git status --porcelain=v1 -z --untracked-files=normal --ignore-submodules=none` in the checkout, with hardening and filter overrides. Any entry is dirty. Ignored files never appear, so the rebuildable installed files (`.ballast/`, `.agents/skills/ballast-*`) and ignored run state do not count (A-8). The remedy names the first ten paths and says to commit or finish them. It never suggests stash or reset (FR-006).
- **Ignored files the update would overwrite** (F-07): ignored files are not dirty, but the update must not overwrite or delete them. R5's pre-mutation check blocks as `dirty` when `OLD..NEW` touches an ignored path. The remedy names the paths and says to move or commit them. A restore never deletes an ignored file, because the check runs before any `read-tree`.
- **Rationale**: The spec's rule is "tracked and untracked-but-not-ignored". That is exactly the set `status` reports without `--ignored`. FR-006 forbids overwriting local files, ignored or not.

## R7. Lock

- **Decision**: `<state_dir>/branch-sync/<sha256(branch)[:16]>.lock`, taken with `draft_pr._Locked`, which gains a `wait` argument (default `LOCK_WAIT`, unchanged for `draft_pr`). `branch_sync` uses `wait=0`: one non-blocking `flock` attempt, then `busy` at once (FR-016, AC-019). `_Locked` already opens with `O_NOFOLLOW | O_CREAT | O_CLOEXEC` and refuses a non-regular file; its `LockUnavailableError` maps to `internal-error` here, because it means the operator state is broken, not that another invocation holds the lock. The lock is held from before the `ls-remote` until the local update, restore or block is complete. The branch's write-ahead record `<key>.json` (R5) sits next to the lock under the same key, so it is read and written only under that lock. `state_dir` already refuses any location under the checkout or a temp root.
- **Rationale**: The operator state directory is outside every agent's write authority. A branch is checked out in one worktree at a time, so a per-branch key covers every same-branch race on one machine. Races across clones are covered by the push lease (R5). AC-020 holds because the second invocation either fails the lock or, in another clone, fails the lease. Reusing `_Locked` keeps one lock implementation.
- **Alternatives rejected**: Waiting for the lock, as `draft_pr` waits up to 60 s. The second invocation would then synchronize again on top of the first, and the spec asks for `busy`.

## R8. Old base and rewritten base

- **Decision**: The pin (R12) keeps `base_commit`, the base commit observed at the last successful check. With `NEW_BASE` the fetched base:
  - `base_commit` absent → `OLD_BASE = merge-base(HEAD, NEW_BASE)`. If there is no merge base, the cause is `diverged`.
  - `base_commit` an ancestor of `NEW_BASE` (the normal case) → `OLD_BASE = merge-base(HEAD, NEW_BASE)`.
  - `base_commit` not an ancestor of `NEW_BASE` (the base was force-pushed), but an ancestor of HEAD and present locally → `OLD_BASE = base_commit`, so only the feature's own commits are replayed.
  - Otherwise, including a `base_commit` that is no longer in the object store → `diverged`, with the remedy to rebase by hand onto the new base.
- **Rationale**: This follows the spec edge case "base rewritten" and never replays old base commits onto the branch.

## R9. Protected-input recheck

- **Decision** (DEC-0002 resolution, F-02):
  - **Before the mutation**: `diff-tree -r --name-only --no-renames -z OLD NEW -- <launcher.BASES>` minus paths under `launcher.SKIPPED` gives the protected names the update will change. They are kept for the report, so the printed names do not depend on a working-tree scan. For the AC-015 fast-forward, `OLD` is the local HEAD and `NEW` the published commit.
  - **After the mutation**, whenever `head_after != head_before` (replay, AC-015 fast-forward, the base-branch fast-forward, a fast-forward with no feature commits, or a completed write-ahead record): `launcher.trusted_inputs(root)` compared with `<state_dir>/trusted.json`, the rule `launcher._refusal` applies. This comparison is the authoritative decision. Any difference is `protected-input`, with the names from the pre-mutation diff (first ten), or the differing digest names when the diff found none.
  - The report says that only the operator runs `ballast trust`, after reviewing the change. The sync itself stays in place, as AC-016 states. The next `ballast run` is refused by the launcher until `ballast trust`.
- **Rationale**: FR-008 and AC-016. The comparison reuses the launcher's own function, so no second definition of the protected set appears. Running it on every HEAD change, as the last step before any non-blocked outcome, closes the path where a push to the published feature branch changes `.specify/` and the fast-forward brings it in unchecked (F-02). This is the one blocked cause that keeps a changed checkout (spec SC-002).
- **Alternatives rejected**: Refusing before the rebase when the base diff touches protected inputs. `ballast trust` could not then accept the change, because the change would not be in the checkout yet (DEC-0002).

## R10. Autonomous runs

- **Decision**: In an Autonomous `start`, the check runs after `write_run`. A block is recorded through `run._stop` as a block in a new category `upstream-sync`, added to `autonomy.BLOCK_CATEGORIES` (F-06):
  - `RECOVERY["upstream-sync"]`: "Remove the cause shown, then start the run again."
  - `recovery_command(run_id, "upstream-sync")` returns `ballast run start --mode autonomous ... (your original start command)`. `BLOCK_COMMAND` already accepts `run start \S.*`. The block's `condition` carries the cause and its own recovery action.
  - `_continue_command` refuses a source run whose current block has category `upstream-sync`: "run RUN_ID stopped before its first agent step; there is nothing to continue. Remove the cause, then start again." Such a block is recorded only before `_launch`, so it always means no agent step ran and no artifact exists for `ballast-continue` to gate.
  - A sync is never recorded through `append_decision` or `append_human_decision` (FR-011). `autonomy.RESUME_REFUSAL` keeps refusing and now points at #21 instead of #18 (A-9).
- **Reading of AC-011**: "the existing block-recovery path" is the block record with its category, recovery text and recovery command, of which restart (`run start`) is already one of the accepted commands. `continue` would start the gate-only `ballast-continue` on a feature with no artifacts and fail at its first validator. This reading is the accepted F-06 fix; it changes no spec text.
- **Rationale**: AC-011 needs a run record to attach the block to. The only Autonomous invocation that runs agent steps and is not refused is `start`, so the record has to exist before the check.
- **Alternatives rejected**: Checking before the record exists and refusing. AC-011 would then have no case.

## R11. Stale plan and review evidence

- **Decision**: After a synchronization that is kept (`synchronized`, or `protected-input`, which keeps it), with `MB = OLD_BASE`, the overlap is `diff-tree -r --name-only --no-renames MB NEW_BASE` intersected with `diff-tree -r --name-only --no-renames MB OLD_HEAD`. That is the set of files both the base and the feature changed. Plan evidence exists when `<feature>/plan.md` exists at `OLD_HEAD`. Review evidence exists when the run's ledger has a `review` or `convergence` event, or `<feature>/reviews/` has a file at `OLD_HEAD`. When the overlap is non-empty and evidence exists:
  - the `branch_sync` event records `overlap` (count), `stale_plan` and `stale_review`;
  - the paths, at most 200, go to `<state_dir>/branch-sync/stale/<sha256(feature)[:16]>/<event_id>.json`, in operator state so an agent can neither plant nor delete one (implementation review SEC-003);
  - the line printed by `ballast run` names the stale evidence and the overlap count;
  - the Draft PR's Ballast section gets one entry per such sync, the newest 20: date, base move and stale evidence, with the first 20 paths as code spans. Records over 16 KiB are skipped.

  The write-ahead record keeps `old_base` and `new_base`, so a sync completed from it (recovery rows 4 and 5) reports the same overlap (E-03).

  The entries never clear themselves. They are dated, so the human approving the merge can compare them with later reviews. No gate is added and no review re-runs (AC-018, FR-015). A fast-forward has no feature commits to replay, so its overlap is empty.
- **Rationale**: The feature's evidence covers what the feature changed. A file both sides changed is where the base may have invalidated it. The ledger stays free of free-form text, as its schema requires; the paths live in operator state, keyed by feature.
- **Alternatives rejected**:
  - Parsing `plan.md`'s Repository Impact table for paths. It is prose and not authoritative for coverage.
  - Clearing the notice after a later review. Evidence from a resumed run and from a continuation lives under different run IDs, so a clearing rule would be easy to get wrong in the direction that hides staleness.

## R12. One feature identity

- **Decision**: The pin `draft_pr` writes at `start` (`<state_dir>/draft-pr/<run>.json`, `{"branch": ...}`) becomes the single identity record. It gains `base` and `base_commit`. The write-ahead record is not in the pin: it is keyed by branch (R5, N-01). `branch_sync` is the pin's only writer; `_launch` stops pinning on its own, so the pin and the check cannot disagree. `draft_pr._branch_pin` keeps reading `branch` only.
  - **`resume`/`continue` without a pin never reach the record** (review 3): they block at R4 step 4, before the recovery table at step 6, so an unpinned run never completes or clears another run's write-ahead record.
  - **When a branch is pinned** (DEC-0006, option B): only at `start`, with the current branch, before the run's first agent step, and for a continuation, with the source run's pinned branch. A failed pin write at `start` is `internal-error`, no longer swallowed by `_launch`. The check never pins a branch after the run's first agent step could have changed HEAD.
  - **No pin at `resume` or `continue`** (DEC-0006, option B): a `resume` of a run with no branch pin, or a `continue` whose source run has none (runs started before #17's pin), blocks as `wrong-branch` with the detail "run {id} has no branch pin (started before branch pinning)" and the recovery "start a new run: your ballast run start command". No pin is written.
  - **`continue`**: the entry point takes `branch` and `base`. `continue` passes the source run's pinned branch and its pinned `base` (which may be absent). The current branch must equal that `branch` or the check blocks as `wrong-branch`. The continuation's pin is written with them only on a non-blocked outcome (N-07, R1).
  - **`base`** (N-06): the base passed in, else the pinned repository's default branch (FR-002), written only after the `ls-remote` that provides it succeeded (R3 step 1). At `start` the check first writes `{branch}`, then adds `base` after the `ls-remote`. A pin left without `base` by a failed `ls-remote`, or written by #17, gets it at its next check; this fills the base from the pinned repository, never the branch from the checkout. The extra advertisement entry costs nothing; the call count stays one (SC-005).
  - `base_commit` is updated after every `up-to-date` or `synchronized` outcome.
- **Rationale**: This is the spec's Feature identity entity, shared with #17 (roadmap item 1), with no second record to drift. The Draft PR keeps taking its base from GitHub's default branch (#17 R5). The two agree unless the default branch is renamed mid-run, and then #17 already reports `base-mismatch`.

## R13. Output, exit status and untrusted text

- **Decision**:
  - `up-to-date` and `synchronized` print one line: `Branch sync: synchronized BRANCH onto BASE (BASE_OLD..BASE_NEW), HEAD OLD -> NEW`, with 12-character short IDs.
  - A block prints `BLOCKED_UPSTREAM_SYNC (CAUSE): DETAIL` and `Recovery: ACTION` on stderr, exits `1` (`EXIT_BLOCKED`), and starts no agent. Ctrl-C during the check is recorded as `internal-error` and exits `130` (`EXIT_INTERRUPTED`), as `run.py` does elsewhere (DEC-0001). The Draft PR checkpoint does not run after a block in a human-gated run.
  - Branch names, paths and Git output never reach a shell. Commands use list argv only (FR-013). Names in remedies are `shlex.quote`d, and paths are passed through `repr` escaping for control characters, as `draft_pr` does. Git's stderr is never printed; causes are classified from exit status and fixed patterns, as in #17 R4.
- **Rationale**: FR-010, SC-003 (one cause, one action), FR-013.

## R14. Testing approach

- **Decision**: Offline `unittest` against real temporary Git repositories. A bare repository on disk stands in for GitHub. The URL builder is the test seam: it returns a `file://` URL in tests, so ls-remote, fetch, lease and rejected push are real Git behavior. A `pre-receive` hook in the stand-in remote simulates a rejected push and records what arrived, and an unreachable path simulates a fetch failure. A second seam raises after a chosen step (after the push, after `read-tree`, after `update-ref`) to simulate a crash; a crash during `read-tree` is simulated by writing part of `new_head`'s files over an `old_head` index, with or without a leftover `index.lock` (P-03). The throwaway runner keeps an argv log in tests, so a scenario can assert where `--attr-source` sits (N-02). A Git version seam lets the 2.41 floor test run on a newer Git. Concurrency uses two processes that both hold a real `flock`. The operator's global configuration is a test file set through `GIT_CONFIG_GLOBAL`, which the gc test uses. The `run.py` harness asserts that no agent step starts after any block: the fake `specify` is never executed.
- **"Unchanged"** (F-08): HEAD, `git ls-files -s`, `git diff-index --cached HEAD`, `git status --porcelain=v1 -z` and the remote branch match their values before the run. The `.git/index` bytes are not compared, because `git status` may refresh the file.
- **Rationale**: Constitution principle 8. Real Git is the behavior being trusted, so faking it would test nothing.

## R15. Which branches synchronization may rewrite

- **Decision** (DEC-0004 option A, DEC-0003, F-04): the branch kind is decided after the `ls-remote` (it needs the default branch):
  - **Feature branch**: the name, split at `/`, `-`, `_` and `.`, has a segment equal to the feature's Issue number in decimal (`18` in `feat/18-branch-sync` or `18-branch-sync`, not in `feat/180-x` or `v18`), and the branch is neither the run's base nor the pinned repository's default branch. The Issue number comes from the feature directory `specs/<N>-<slug>` (`draft_pr` `ISSUE` pattern), from operator state only (implementation review SEC-002): the `-i feature_directory` input at `start`, which the check pins with the branch, and that pin at `resume` and `continue` (a continuation's pin is its source run's). A pin without the feature blocks as `wrong-branch` like a pin without the branch (DEC-0006). `run.py start` refuses a missing, invalid or repeated `-i feature_directory` during argument validation, before any check or pin (E-01); a check with no feature directory is therefore reachable only through the module API, and it still blocks as `not-feature-branch` when behind, as defense. `ballast run` starts only the feature workflows, which always name a feature directory; bugfix and assess runs started with `specify` directly do not pass through `ballast run` and are not synchronized (spec edge case, N-08). ADR-0005 and the policy section say so.
  - **One predicate** (N-05): `autonomy.is_feature_branch(name, issue, base, default_branch)` is the only definition. `branch_sync` calls it for R15, and `autonomy.check_eligibility` calls it instead of its own "not `HEAD`, not the default branch" test (with `base` = the default branch, which a new Autonomous run records). `BRANCH_REFUSAL` becomes "autonomous needs a feature branch named for the Issue without an open PR". It lives in `autonomy` because `branch_sync` already imports `autonomy` (for `GIT_HARDENING`) and `autonomy` imports only `launcher`: placing it in `branch_sync` would create an import cycle.
  - **Base branch**: the branch equals the run's base. When behind, it is fast-forwarded locally to the base when HEAD is an ancestor of it. It is never replayed and never pushed. Local-only commits block as `diverged` with the recovery `git switch -c BRANCH` (DEC-0003).
  - **Other**: never rewritten and never pushed. When behind, the run blocks as `not-feature-branch` with the recovery "synchronize {branch} yourself, or run the feature on its own branch: git switch -c {feature-branch}". When up to date, the run proceeds; AC-015 fast-forwards to the published branch still apply, because they rewrite nothing.
- **Rationale**: A lease prevents lost commits, not rewritten shared history. Before the launcher gains force-push authority, the set of branches it may rewrite must be fixed in code. The Issue number is the convention Ballast already uses for the feature directory and its own branches. ADR-0005 states this rule.
- **Alternatives rejected**: An operator allowlist of branch patterns in `ballast.toml` (DEC-0004 option B), not chosen by the operator.
