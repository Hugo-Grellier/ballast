## New findings, by severity

### N-01 — high — implementation bug (design): the write-ahead record is keyed by run ID, so the F-06 recovery path cannot complete a half-done sync

- **Where**: `research.md` R5 step 2 and the recovery table; R10; R12; `data-model.md` § Feature identity (pin) `sync`; `contracts/branch-sync.md` guarantee 8; `quickstart.md` 18.
- **Problem**: The record is written into `<state_dir>/draft-pr/<run_id>.json`. R4 step 6 reads *this run's* pin. Every path that reaches the next invocation under a different run ID never sees it: (a) an Autonomous `start` that pushed and then blocked (`busy`, `internal-error`, Ctrl-C) has, per R10/F-06, the recovery command `ballast run start --mode autonomous ...`, which draws a fresh `uuid4` in `_start_autonomous` and writes a fresh pin; (b) `continue` draws `new_id` and writes the continuation's pin from the source pin's `branch` and `base` only (R12 does not copy `sync`); (c) a human-gated operator who starts a new run on the same branch. In all three, the next check observes published `== NEW` and local `== OLD`, where `NEW` is a replay and not a descendant of `OLD`, and classifies `diverged` with the manual `git pull --rebase` recovery. That is exactly the state F-03 was accepted to remove, and for Autonomous runs it is the *only* recovery path, so guarantee 8 ("completed by the next invocation without a manual step") is false for them. Scenario 18 reruns `resume` under the same run ID and so cannot see it.
- **Fix**: Store the write-ahead record per branch, not per run: `<state_dir>/branch-sync/<key>.json` next to the lock (same key, same `0600`/`0700`, same atomic replace), holding `{branch, old_head, new_head, published_old, run_id, written_at}`. Step 6 reads it for the current branch regardless of run ID; the pin keeps `branch`, `base`, `base_commit` only. Keep the recovery table unchanged. Record the originating `run_id` so the `recovered` event can name it. Add to scenario 18: "second invocation is `start --mode autonomous` (new run ID)" and "second invocation is `continue`"; both must end `synchronized` with `recovered` true.

### N-02 — high — implementation bug (design): `--attr-source` is a top-level `git` option and needs Git 2.41, not 2.40

- **Where**: `research.md` R2 step 1 (`git merge-tree --write-tree --merge-base=C^ --attr-source=NEW_BASE PARENT C`) and R2 § Requirement; `contracts/branch-sync.md` § External commands; `plan.md` § Technical Context ("`git` 2.40 or later (`merge-tree --merge-base` and `--attr-source`)"); DEC-0001 detail text and `ballast doctor` floor; quickstart 36.
- **Problem**: **Reproduced** on Git 2.53: `git merge-tree --write-tree --merge-base=OLD --attr-source=BASE BASE C` exits 129 with `error: unknown option 'attr-source=...'`. `git --attr-source=BASE merge-tree --write-tree --merge-base=OLD BASE C` exits 0 and merges the `merge=union` case clean; `GIT_ATTR_SOURCE=BASE` in the environment does the same. As written, every replay would end as `internal-error`, and scenario 8 would fail. The option is the global `git --attr-source=<tree-ish>` added in Git 2.41 (release notes: "`git` learned the `--attr-source=<tree>` command line option"); `merge-tree --merge-base` is 2.40. Round 1 stated the 2.40 floor for both; that was wrong on `--attr-source`.
- **Fix**: Argv `[git, "--attr-source=" + NEW_BASE, *GIT_HARDENING, *NO_MAINTENANCE, "merge-tree", "--write-tree", "--merge-base=" + PARENT_OF_C, "--name-only", "-z", PARENT, C]` (the global option goes before the subcommand; `-c` flags are also global and may follow). Raise the floor to 2.41 everywhere it appears: plan, R2, DEC-0001 detail ("git X.Y is older than 2.41"), contract, `ballast doctor`, quickstart 36, the policy section. Scenario 8 then verifies the placement; add an assertion that `merge-tree` was invoked with the option (a `GIT_TRACE` capture or the test seam's argv log).

### N-03 — medium — implementation bug (design): the recovery table has no row for a local branch that advanced beyond `old_head`, and the completion-blocked `dirty` advice leads straight into it

- **Where**: `research.md` R5 recovery table and "A completion blocked by its own pre-mutation checks ... keeps the record and reports that cause"; `contracts/branch-sync.md` `dirty` recovery ("commit or finish these changes ... then rerun").
- **Problem**: After a successful push (`P == new_head`) with the local branch still at `old_head`, two realistic sequences leave `L` a descendant of `old_head` and `P == new_head`: (a) the completion is blocked `dirty`, the operator follows the printed recovery and *commits*, then reruns; (b) the operator commits in another terminal between the push and the CAS `update-ref`, which is the `busy` case R5 names. Both land in "anything else → clear the record, continue", and the normal classification sees two branches with commits the other lacks: `diverged`, manual `git pull --rebase`. The launcher created the state and its own advice completes the trap.
- **Fix**: Add the row "`L` descends from `old_head` and `L != old_head`, `P == new_head`: replay `old_head..L` onto `new_head` with the R2 machinery (old base `old_head`, new base `new_head`), push with lease `new_head`, local update, clear; `recovered` true". That reuses the replay, needs no new primitive, and makes the record safe to keep across an operator commit. Until then, at minimum the completion-blocked `dirty` detail must say "a previous synchronization already pushed {new_head}; move these changes aside without committing, then rerun". Add both sequences as scenarios.

### N-04 — medium — implementation bug (design) / spec violation (FR-012, AC-017): checkout-side object probes lazily fetch through agent-writable `origin` configuration in a partial clone

- **Where**: `contracts/branch-sync.md` § External commands, "In the checkout": `cat-file -e`, `merge-base --is-ancestor`, `rev-list`, `diff-tree`; `research.md` R3 step 2 ("When the base or published commit is missing locally (`cat-file -e`)").
- **Problem**: **Reproduced**: in a `--filter=blob:none` clone, `git cat-file -e <commit only on the remote>` spawns a `fetch` from the promisor remote (the checkout's `origin`, with its `core.sshCommand`, `insteadOf`, `credential.helper` from `.git/config`) and returns 0 with the object now present. R3's probe asks precisely for a commit known to be missing, so in a partial clone the "no fetch when both commits are local" path performs a network fetch under agent-writable configuration on every invocation, which is what R2/R3/R3a exist to prevent. `merge-base`, `rev-list` and `diff-tree` can do the same for missing trees in a treeless clone. The exposure exists today in #17's checkout-side commands, but this feature makes it deterministic. `GIT_NO_LAZY_FETCH=1` makes the same probe exit 1 (reproduced); it exists from Git 2.46.
- **Fix**: Run the existence probe in the throwaway (`cat-file -e` there has no promisor remote; it reads the shared object store). Set `GIT_NO_LAZY_FETCH=1` in the environment of every checkout-side command; below 2.46 the variable is ignored, so additionally read `extensions.partialClone` / `remote.*.promisor` from the checkout's config as data and block as `git-unavailable` with the detail "partial clone needs git 2.46 or later". Add a scenario with a blobless scratch clone: no fetch through `origin` (a `core.sshCommand` marker stays absent), the throwaway fetch supplies the objects.

### N-05 — medium — architecture issue: two definitions of "feature branch"

- **Where**: `research.md` R15; `autonomy.check_eligibility` (`BRANCH_REFUSAL`: branch is not `HEAD`, not the default branch, and has no open PR); `plan.md` § Repository Impact (`autonomy.py` changes do not mention it).
- **Problem**: An Autonomous `start` on `develop` passes eligibility, then blocks `not-feature-branch` at the check when behind, or proceeds when up to date and is later pushed by the publisher's `_push` (no lease) under the weaker rule. The constitution and `CLAUDE.md` forbid a second source of truth for a boundary ADR-0005 is about to state.
- **Fix**: One predicate `branch_sync.is_feature_branch(name, issue, base, default_branch)` used by both R15 and `check_eligibility` (which already has the issue and the default branch). The Autonomous eligibility message gains "named for the Issue". Record it in the plan's `autonomy.py` row and ADR-0005; one test in `test_autonomous_run.py`.

### N-06 — low — spec ambiguity: pin `base` depends on the `ls-remote` that runs one step later, and the first `ls-remote` cannot name `refs/heads/BASE`

- **Where**: `research.md` R4 step 4 ("with no pin, write one"), R12 ("`base` is recorded when the pin is written ... else the pinned repository's default branch"), R3 step 1 (`ls-remote --symref URL HEAD refs/heads/BASE refs/heads/BRANCH`); `data-model.md` (`base` set "with `branch`, or on the first check of a pin that lacks it").
- **Fix**: State the two-phase write: step 4 writes `{branch}`; step 5 runs `ls-remote --symref URL HEAD refs/heads/BRANCH` when `base` is unknown, then a second `ls-remote` for `refs/heads/BASE` (or one call with both when `base` is known), then fills `base`. A pin left without `base` by a failed `ls-remote` is completed on the next invocation. Count the extra call in SC-005 for the first check only.

### N-07 — low — implementation bug (design): a blocked `continue` leaves a phantom run archive

- **Where**: `research.md` R1 ("The new run ID is drawn before the check, so the check's ledger event and pin belong to the continuation. A blocked continuation then changes no record"); contract § Call sites.
- **Problem**: `ledger.append` creates `<common dir>/speckit-runs/<new_id>/events.jsonl` for a run that `autonomy.new_run` never records; each retry draws another ID. Reports and `ballast ledger` listings then show runs with one `branch_sync` event and nothing else.
- **Fix**: Either record a blocked continuation's event under the source run (its ledger already exists and the block belongs to the attempt to continue it), or state that phantom archives are accepted and that `report` tolerates a stream holding only `branch_sync`. Decide in the plan; add the assertion to scenario 4.

### N-08 — low — spec ambiguity: the "bugfix and assess through `ballast run`" edge case is vacuous and DEC-0004 would block them

- **Where**: `spec.md` § Edge Cases (last bullet); `research.md` R15 ("A run with no feature directory has no Issue number and therefore no feature branch"); `run.py` `WORKFLOW = "ballast-feature"`; `bugfix` and `assess` inputs are `report|idea` and `slug`, no feature directory.
- **Problem**: `ballast run start` runs only `ballast-feature`, so the edge case cannot occur today; the day those workflows get a `ballast run` path, option A has no Issue number for them and every behind branch blocks. Not a defect now, but ADR-0005 should not be silent about it.
- **Fix**: One sentence in ADR-0005 and the policy section: "a run without an Issue number (bugfix, assess) is never synchronized by rewrite; it blocks `not-feature-branch` when behind until a later decision". Keep the spec bullet or drop it.

### N-09 — low — implementation bug (design): GUI askpass programs are not covered by `GIT_TERMINAL_PROMPT=0`

- **Where**: `research.md` R3a § Environment; F-11.
- **Problem**: `GIT_ASKPASS`, `core.askPass` and `SSH_ASKPASS` are consulted before the terminal; a GUI helper in the operator's session pops a dialog and the network command waits for its timeout (600 s on `fetch`), which scenario 39 ("no wait for the timeout") does not reproduce because the test has no askpass.
- **Fix**: Set `GIT_ASKPASS=""` (an empty value skips `core.askPass` and `SSH_ASKPASS` and falls to the disabled terminal prompt) and `SSH_ASKPASS_REQUIRE=never` (OpenSSH 8.4+) in the throwaway environment. Add an askpass marker program to scenario 39.

### N-10 — low — spec ambiguity: order of the base-branch fast-forward and the dirty check

- **Where**: `research.md` R4 step 10 (base branch fast-forwarded) precedes step 11 (`dirty`); `data-model.md` § State transitions lists `base → fast-forward` before `dirty → blocked(dirty)`; R5 step 1 applies "before anything is pushed".
- **Fix**: State that every fast-forward (AC-015, base branch, no feature commits, record completion) goes through R5 steps 1, 2, 4 and 5 (push only for the published feature branch), so a dirty tree on the base branch blocks `dirty` and never carries uncommitted changes across a `read-tree`. Scenario 29 should add a dirty variant.

### N-11 — low — implementation bug (design): recovery probes must tolerate a missing `new_head`

- **Where**: `research.md` R5 recovery table rows 3 and 4; `data-model.md` ("A pin whose `sync` fails validation is treated as having no record").
- **Problem**: For an unpublished branch, `new_head` between the record write and `update-ref` is an unreferenced loose object in the checkout; the checkout's own gc (an agent's `git gc --prune=now`, or two weeks of auto-gc) can delete it while the index already references its blobs (the index keeps blobs alive, not the commit). `diff-index --quiet new_head` then fails with "bad object", which the table does not classify. Also, the row-4 probe depends on fresh stat information; `git status` in R6 refreshes it, so state that dependency, or use `diff-index --cached --quiet new_head` plus `diff-files --quiet` (reproduced: both agree after a refreshed `read-tree -m -u`).
- **Fix**: `cat-file -e new_head` first; missing and `P != new_head` → "anything else" (clear, continue; the classification then reports `dirty` from the staged tree with the normal recovery). Treat an invalid `sync` record as `internal-error`, not as "no record": the file is operator-only, so an invalid one is a Ballast bug, and clearing it silently can hide a landed push.

### N-12 — low — missing test / design: shallow checkouts

- **Where**: `research.md` R3, R4 step 9, R8.
- **Problem**: A checkout with `.git/shallow` answers `merge-base --is-ancestor` and `merge-base` through grafts the throwaway does not see, and negotiation from `refs/haves/HEAD` promises ancestors the checkout lacks. Shallow dev checkouts are rare on the qualified host but cheap to refuse.
- **Fix**: `rev-parse --is-shallow-repository` true → `git-unavailable` with the detail "shallow checkout; run git fetch --unshallow", or document it as unsupported in the policy section. One scenario.

## Recommendations on the two open points

1. **SC-002 after a successful push**: amend SC-002 with the second exception and complete forward on the next invocation; do not push back with a lease. Reasons: a push back is a second rewrite of a shared ref and can fail in the same ways as the local update did (then the record is needed anyway, so the push-back buys no simplification); it discards a push that already succeeded and whose content is exactly what the operator asked for; forward completion is idempotent, observable from the two branches (BL-INV-005), and already what the record is for. Conditions: N-01 (the record must be branch-keyed or the completion does not happen on the Autonomous restart), N-03 (the one reachable state the table lacks), and a cause-specific detail for the post-push block: "the published branch already holds {new_head}; rerun to finish the local update" with the recovery "rerun", so SC-003 still gives one action. Suggested SC-002 text: "In every blocked case, except `protected-input` (AC-016, DEC-0002) and a failure after the push succeeded, where the published branch holds the synchronized commit and the next invocation completes the local branch (research R5), the branch HEAD, index, working tree and published branch are byte-for-byte the same before and after the invocation."

2. **`resume` of a run with no pin**: keep the plan (pin the current branch at `resume`). Reasons: with the check writing the pin before `_launch`, a failed pin write at `start` becomes `internal-error`, so the unpinned population is only runs started before #17, which closes with time; whatever branch an agent switched to earlier, R15 bounds what can be rewritten (`main` → fast-forward only, `develop` → never rewritten, a branch named for the Issue → the intended branch); the operator is present at a human-gated `resume` and Autonomous `resume` stays refused (A-9); `wrong-branch` would have no pinned name to put in its recovery, so its only advice is "start a new run", which the operator can choose anyway. Required: print "Branch sync: pinned {branch} at resume (run started before pinning)" so the choice is visible, and record `pinned_at_resume` nowhere in the ledger (no new field); scenario 11 asserts the line.
