## Crash-point table

Record `{old_head, new_head, published_old}`, local HEAD `L`, observed published commit `P`. "Pub" is a published feature branch after a replay (the record carries `published_old != new_head`); "Unpub" is an unpublished branch (`published_old` null); "FF" is an AC-015 or base-branch fast-forward record (`new_head == P`, `published_old` equal to `P` or null; nothing is pushed). "Concurrent" is a second `ballast run` on the same branch at that moment. Row numbers are the current R5 table; "→" names the row the state lands in on the next invocation.

Every point lands in exactly one row; row order is deterministic (first match). No point loses a commit: `new_head` is pushed before any local change, the CAS never moves a ref that is not at `old_head`, and no row deletes an ignored file (row 3 touches no file; rows 4 and 5 re-run the ignored-path intersection before `read-tree`). The defects are three states whose row gives an outcome the operator cannot act on (E, F with an edit, L) and one state whose row pushes outside the rewrite boundary (K on a fast-forward record). The concurrency column holds throughout: the lock is `flock`, released when the holder dies, so a crashed invocation never wedges the branch; a second clone is coordinated only by the lease, and after a replay it sees the normal `diverged` with `git pull --rebase` (AC-013), which is inherent to rewriting, not to the crash.

## Findings, by severity

### P-01 — high — spec violation (FR-005, DEC-0003, DEC-0004, guarantee 3): row 5 pushes a branch whose record pushed nothing

- **Where**: `research.md` R5 row 5 and "Every fast-forward is an R5 mutation" (R4); `contracts/branch-sync.md` guarantee 3; `data-model.md` § Write-ahead record (`published_old`).
- **Problem**: Every fast-forward writes a record. For the AC-015 fast-forward the record is `{old_head: L, new_head: P, published_old: P}`; for the base-branch fast-forward `published_old` is null but `P == new_head` because `BRANCH == BASE`. The branch kind (R15) is decided at R4 step 7, *after* the table runs at step 6, so no row can consult it. Sequence: `main` (or `develop`) strictly behind its published branch, clean; record written; crash before `update-ref` (points B, D, E, F); the operator commits on the old local branch; rerun. Row 5 matches (`L` descends from `old_head`, `L != old_head`, `P == new_head`) and its action is "replay onto `new_head`, then R5 steps 1–5 with the lease `new_head`", which pushes `main` or `develop`. That is the push DEC-0003 and DEC-0004 forbid, performed by the recovery path, and scenario 29's `pre-receive` assertion does not cover it. The correct outcome for that state is the normal one: both branches have commits the other lacks → `diverged`, `git pull --rebase`.
- **Fix**: Row 5 (and, for symmetry, row 2) applies only when the record describes a push Ballast made: `published_old` non-null and `published_old != new_head`. Otherwise the state is row 7. State the invariant under the table: "no recovery row pushes unless the record records a push; a fast-forward record never does". Also state that R5 step 3 is skipped when `NEW == OBSERVED` (the AC-015 case would otherwise issue a no-op push and open the 600 s window for nothing), which is what makes `published_old == new_head` the marker. Scenario: AC-015 on `main` and on `develop`, killed between the record and `update-ref`, a commit, rerun → `diverged`, `pre-receive` records no push, record cleared.

### P-02 — medium — implementation bug (design): row 3 is stricter than `update-ref` needs, and every miss lands in a `dirty` the operator cannot clear

- **Where**: `research.md` R5 row 3 and the row-3/row-4 ordering note; the post-push `dirty` advice; `contracts/branch-sync.md` post-push `dirty` row; `quickstart.md` 18.
- **Problem**: Row 3 requires `diff-files --quiet`, "no untracked entries", a prior `status` refresh, and `P == new_head`. None of them is needed: `read-tree -m -u` writes the index last, so index `== new_head` already proves the worktree update completed, and `update-ref` touches no file. **Reproduced**: after `read-tree -m -u OLD NEW`, an edit to a tracked file and a new untracked file leave `diff-index --cached --quiet NEW` at 0, the CAS succeeds, and `status` afterwards shows exactly ` M g` and `?? untracked`, the operator's own state. With the strict row, that same state falls to row 4, whose R5 step 1 runs `status` against `HEAD == old_head` and reports every base change as staged, so the block is `dirty` "a previous synchronization already pushed …; uncommitted changes: {the sync's own staged paths}" with the recovery "move these changes aside without committing them", which cannot be done for staged changes. The strictness converts a one-command completion into a dead end whenever the operator touched the tree between the crash and the rerun, which is the usual case (they ran `git status` and reacted). The `P == new_head` condition has the same effect when the published branch moved on after Ballast's push: finishing the local update first and classifying `L == new_head` against `P'` is strictly better than leaving a staged tree.
- **Fix**: Row 3 is "`L == old_head` and `diff-index --cached --quiet new_head`" and nothing else; action unchanged (CAS `old_head → new_head`, clear, `recovered` true, then step 14). Drop the `status`-refresh sentence. Scenario 18: after the kill between `read-tree` and `update-ref`, edit a tracked file and add an untracked file before the rerun; expect `synchronized`, `recovered` true, and `status` showing exactly those two entries.

### P-03 — medium — implementation bug (design) / missing test: a crash during `read-tree -m -u` has no row, and a stale `index.lock` is not classified

- **Where**: `research.md` R4 step 3 (in-progress markers), R5 step 4 and the table; `data-model.md` `in-progress` and `dirty` rows; `quickstart.md` 18, 34.
- **Problem**: **Reproduced** with 40 000 files: SIGKILL during `read-tree -m -u OLD NEW` leaves the index at `OLD`, 3 096 files at `NEW` content, and `.git/index.lock`. With the lock present `status`, `diff-index` and `diff-files` still work (exit 0) and `update-ref` succeeds, but `read-tree` and `read-tree --dry-run` exit 128 ("Unable to create index.lock: File exists"), which R5 step 1 classifies as `dirty` "untracked files are in the way". Ctrl-C (scenario 34's signal) removes the lock but stops the same way, since checkout-side commands are not in a new session. On the rerun: published → row 4 → `dirty` on the half-written paths with "move these aside without committing"; unpublished → row 6 clears the record, the replay runs again, step 11 blocks `dirty` "commit or finish these changes" on the same paths, asking the operator to commit `read-tree`'s output as their own work. `read-tree -m -u OLD NEW` cannot resume by itself ("Entry 'd/f1' not uptodate. Cannot merge.", reproduced), and the window is the whole local update, so it is the one interruption point the table does not cover.
- **Fix**: (a) R4 step 3: `index.lock` present (`rev-parse --git-path index.lock`) → `in-progress` with the detail "another git process may hold the index ({path} exists)" and the recovery "if no git process is running, remove it, then rerun" (Git's own wording); it must come before any `read-tree`. (b) A row 3b, between rows 3 and 4: `L == old_head`, `diff-index --cached --quiet old_head`, and every `status` entry, untracked ones included, is a path of `diff-tree -r old_head new_head` whose `hash-object` (filters disabled, as every checkout-side command runs) equals `ls-tree new_head`'s blob; meaning "interrupted during `read-tree`". Two acceptable actions: the minimal one blocks `dirty` with the detail "an interrupted update left these files at the synchronized content: {paths}" and the single recovery `git restore --source={new_head} --staged --worktree .` (**reproduced**: it removes files `new_head` deletes, leaves index and worktree equal to `new_head`, and the rerun then lands in row 3, so no second manual step); the automatic one stages those paths with `update-index --add --cacheinfo mode,oid,path` and runs R5 steps 4 and 5 (**reproduced**: the 2-way `read-tree` then accepts the entries). Take the minimal one: it is a crash-only path, adds no primitive to the checkout-side list, and never writes a file; say in guarantee 8 and in the DEC-0005 paragraph that this one case needs the printed command. Any dirty path that fails the hash test is the operator's and gets the existing advice. Scenarios: killed during `read-tree` with `index.lock` left (expect `in-progress` first, then the row 3b outcome after the lock is removed) and Ctrl-C during `read-tree` (no lock; row 3b at once); both published and unpublished.

### P-04 — medium — implementation bug (design): the failed-CAS restore targets a commit HEAD no longer is

- **Where**: `research.md` R5 step 4 ("The tree is restored with `read-tree -m -u NEW OLD` only while the index and working tree still equal `NEW`"); `plan.md` Review notes ("the CAS-failure restore runs only while the tree is still exactly `NEW`"); `quickstart.md` 40 ("tree left as the commit made it").
- **Problem**: The CAS fails only when the ref is no longer at `OLD`, so after a failed CAS `HEAD` is some `X != OLD` and restoring the tree to `OLD` never matches it. **Reproduced**: `read-tree -m -u OLD NEW`, then a bare `git commit` of the staged tree in another terminal (the natural reaction to `git status` showing staged changes) gives `X` with `X^{tree} == NEW^{tree}`; the CAS fails; both guards pass; the restore leaves `M  f` and `D  h` against `X`. The next invocation reaches row 5 (`X` descends from `old_head`, `P == new_head`), replays nothing (the commit is already upstream, reproduced with `merge-tree`), and its R5 step 1 blocks `dirty` on the restore's own output with "move these changes aside without committing". Scenario 40 expects the opposite ("tree left as the commit made it"), so the plan and its test disagree. The guard "tree is exactly `NEW`" is right; the target is wrong.
- **Fix**: Restore to the current HEAD's tree: `read-tree -m -u NEW HEAD`, under the same two guards (**reproduced**: the tree is then clean against `X`; when `X^{tree} == NEW^{tree}` it is a no-op). The rule reads: "after a lost CAS, when the index and worktree hold nothing but the sync's output, make them match whatever HEAD now is; otherwise leave them". Scenario 40, second variant: a bare commit of the staged tree → `busy`, tree clean at `X`; rerun → row 5 drops the empty replay and completes to `new_head` (local update `X → new_head`, no-op push), `recovered` true.

### P-05 — low — spec ambiguity (FR-008): a crash after `update-ref` skips the recheck of that HEAD change

- **Where**: `research.md` R5 row 1 ("clear the record, continue the check"), R4 step 14 ("whenever HEAD changed in this invocation"), R9.
- **Problem**: Point H moved HEAD in the crashed invocation; the rerun's row 1 clears the record and HEAD does not change in that invocation, so step 14 never runs for the change the crash brought in. It is covered, but by the launcher: `launcher._refusal` compares the protected inputs before `run.py` executes at all, so a `.specify/` or `ballast.toml` change at `new_head` refuses the rerun before the check runs. The plan should say that rather than let a reader of row 1 conclude the recheck was lost.
- **Fix**: One sentence under row 1, and a scenario: killed after `update-ref` with a base change under `.specify/`; the next `ballast run` is refused by the launcher (no check runs, no event), `ballast trust`, then `up-to-date`.

### P-06 — low — spec ambiguity (SC-003): the post-push `dirty` row lacks the ignored and untracked variants

- **Where**: `contracts/branch-sync.md` `dirty` (completing a synchronization already pushed); `research.md` "A block after a successful push".
- **Problem**: Row 4's completion re-runs R5 step 1 after the push, so "ignored files would be overwritten: {paths}" and "untracked files are in the way: {paths}" are reachable after a push (an ignored or untracked file created at a path `new_head` adds, since the crash). The contract's post-push row gives only the "uncommitted changes" detail; the generic rows lack the "already pushed {new_head}" prefix and the "rerun to finish the synchronization" ending.
- **Fix**: Make the post-push row cover all three details with the "move or commit these files, then rerun to finish the synchronization" recovery.

## Partial clones: refuse now, keep the design for later

**Recommendation: refuse partial clones in this feature, the way shallow checkouts are refused**, and keep `GIT_NO_LAZY_FETCH=1` on every command as defense in depth. Reasons, in order of weight:

1. **The printed recovery does not work.** **Reproduced** on a fresh blobless clone: `git fetch --refetch origin` re-applies the configured `blob:none` filter and the blob stays absent; `git fetch --refetch --no-filter origin` fetches everything (`rev-list --missing=print --all` empty) but leaves `remote.origin.promisor=true` and `partialclonefilter=blob:none`, so the plan's own detection still reports a partial clone and the next lazy fetch is one `git` command away. A working conversion is three commands (`fetch --refetch --no-filter`, unset `remote.origin.promisor`, unset `remote.origin.partialclonefilter`, plus `extensions.partialClone` on older clones), or a fresh clone.
2. **The blob check's necessity depends on the server, so scenario 41 cannot prove the property against GitHub.** **Reproduced**: with `refs/haves/HEAD` sent and ACKed (packet trace), Git 2.53's `upload-pack` still delivered a blob that the sparse-cone checkout lacked and that sat in the edge tree at another path, because `pack.useSparse` dedupes per path. A server without the sparse walk withholds the same blob and `read-tree` fails after the push. The check is cheap insurance, but the test suite can only exercise one of the two server behaviors, and the stand-in remote needs `uploadpack.allowFilter` to be a partial clone at all (my first attempt silently cloned a full repository: "filtering not recognized by server").
3. It adds a second Git floor (2.46) with its own seam, three scenario variants, and the null-OID filtering of `diff-tree` output that `cat-file --batch-check` otherwise reports as "missing" (hit in the experiment), all inside an R2 boundary, for a checkout shape the qualified host does not use.

Concretely: R3a "Partial and shallow checkouts" becomes one rule, `remote.*.promisor` or `extensions.partialClone` set → `git-unavailable` with the detail "partial clone" and the recovery "clone the repository again without --filter, or: git fetch --refetch --no-filter origin && git config --unset remote.origin.promisor && git config --unset remote.origin.partialclonefilter, then rerun"; drop the blob-presence step from R5 step 1, the 2.46 row from the contract and data model, and scenario 41's first and third variants (keep a single "blobless clone → refused, no fetch through `origin`" variant); keep the support design in research as the recorded extension ("later: Git 2.46, `GIT_NO_LAZY_FETCH`, blob presence of `diff-tree old new` minus null OIDs, sparse-cone scenario"). If the operator prefers to keep support, the minimum is: the `--no-filter` recovery above, the null-OID filter, and a `--sparse` variant of scenario 41 so the withheld-blob path is exercised at least where Git can be made to withhold it.
