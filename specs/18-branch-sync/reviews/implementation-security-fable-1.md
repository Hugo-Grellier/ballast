Where agent-writable data could select an authority input, traced:

| Input | Source | Agent reach |
| --- | --- | --- |
| branch rewritten/pushed | pin at `start` (operator state), must equal current HEAD | can only cause `wrong-branch` |
| base | pin `base`, else `ls-remote --symref HEAD` of the pinned repository | none |
| repository URL | `ballast.toml` (protected input) | scheme only (`https` vs `ssh`), same host and path |

## Findings

### High

#### SEC-001: `git status --ignore-submodules=none` runs a clean filter from a nested repository's own configuration

- Label: spec violation (FR-012, AC-017; ADR-0005 "No program named by its configuration, attributes or hooks runs"; constitution BL-INV-002), implementation bug
- Location: `tools/spec_workflow/branch_sync.py:1032-1043` (`status()`, `--ignore-submodules=none` at 1037), reached from `dirty()` (1045), `follow_published` (1274), `rebase_feature` (1322), `mutate` (1470, 1476), `interrupted_update` (1194)
- Evidence: `autonomy.filter_flags` neutralizes only the filter drivers listed by `git config --list` **of the superproject**. With `--ignore-submodules=none`, `git status` spawns `git status --porcelain=2` inside every populated gitlink (`is_submodule_modified`), and that child reads the nested repository's own config. Reproduced in `/tmp/bsync-review-sub`: superproject with 0 `filter.*` keys, a submodule whose `.git/config` (or a plain nested `sub/.git`, which an agent can write without `submodule add`) defines `filter.evil.clean = touch MARKER; cat`, a `.gitattributes` selecting it and one modified tracked file. `git -c core.hooksPath=/dev/null -c core.fsmonitor=false -c submodule.recurse=false status --porcelain=v1 -z --ignore-submodules=none --untracked-files=normal` created the marker; the same with `--ignored=matching --untracked-files=all` (the `mutate` listing) created it too. With `--ignore-submodules=dirty` the marker was not created and the submodule was not spawned; with `all` likewise. An agent needs only its sandbox write authority (a gitlink entry via `update-index --cacheinfo 160000`, a nested `.git` directory, a config and an attributes file) and the next `ballast run` on a branch that is behind or whose published branch is ahead; the program runs in the operator's process tree with the operator's authority before any push decision.
- Fix: pass `--ignore-submodules=dirty` (gitlink pointer changes still report, no process is spawned in the submodule) on every `status` in `branch_sync.status()`; keep `submodule.recurse=false`. Since `read-tree -m -u` never enters submodule worktrees with `submodule.recurse=false`, nothing is lost for safety. Check `autonomy.git`/`tree_digest` for the same flag before the autonomous publisher reuses it (out of this feature's diff, note only).
- Test: in `TrustBoundaryTests`, extend `test_checkout_configuration_never_runs` with a nested repository under the checkout (gitlink in the index, `sub/.git/config` filter + `.gitattributes` + modified file) and assert the marker never exists after `synchronized`; also assert a staged gitlink change still blocks as `dirty`.

### Medium

#### SEC-002: the Issue number that gates rewrite and push is read from agent-writable run state on `resume`

- Label: architecture issue (AC-017 "no agent can ... influence it", FR-005; contract § Entry point "validated feature directory"), spec ambiguity (the contract does not say the Issue number must come from operator state)
- Location: `tools/spec_workflow/run.py:300-318` (`_run_feature`, `.specify/workflows/runs/<run>/inputs.json` at 307), consumed at `branch_sync.py:502-508` (`self.issue`) and `1230-1237` (`kind()`); `run.py:966` passes it for `resume`
- Evidence: the branch is pinned in operator state at `start`, but on a human-gated `resume` the Issue number, the only other input of `is_feature_branch`, comes from a file the agent can write. If an operator started a run on a branch with a numeric segment that is not the Issue (`release/3.1`, `v2-hotfix`, `team-42/x`), the rule blocks it as `not-feature-branch`; an agent that sets `feature_directory` to `specs/3-x` would have it rebased and lease-pushed. Today this is closed by a control in another module: `agent._protected_state` digests `.specify/workflows/runs/**` around every agent step (`agent.py:99`, `SPECIFY_WRITABLE`), an edit marks `BALLAST_TAMPERED`, the launcher refuses before the check runs, and the in-progress marker covers a wrapper that died mid-step. The preventive design (operator state decides every authority input) therefore rests on a detective control that neither the contract nor ADR-0005 names, and `draft_pr.identify` depends on it as well.
- Fix: write `feature` into the operator pin at `start` (the check already writes the pin before the first agent step; `continue` already inherits the source run's `feature` from the operator record). On `resume`, take `issue` from the pin; when the pin predates the field, use `issue=None` (fails closed as `not-feature-branch` when behind). Keep the `inputs.json` value only for the ledger event's feature field (pattern-checked by `ledger.validate`). Record in the contract that the rewrite rule's inputs are all operator state.
- Test: `ResumeOnCurrentBaseTests`: pin branch `release/3` with feature `specs/18-x`, advance the base, write `{"inputs": {"feature_directory": "specs/3-x"}}` to the run's `inputs.json`, call the `resume` path (`run.main(["resume", RUN])` in `test_spec_workflow`) and assert `not-feature-branch`, no push, snapshot unchanged.

#### SEC-003: stale-evidence records live in the agent-writable common directory, are read without bounds and can carry a markdown link

- Label: architecture issue (security policy: "Treat Markdown ... as untrusted ... review derived claims before writing them"; data integrity of the Draft PR section), implementation bug (no size or count bound), missing test
- Location: writer `branch_sync.py:1731-1748`; reader `draft_pr.py` `_stale_entries` (glob over `<common dir>/speckit-runs/*/branch-sync/*.json`, `json.loads(path.read_text())`) and `_stale_record` (path rendering with `_escape(_printable(path))`); `data-model.md:132-141`
- Evidence: for a primary checkout `.git/speckit-runs` is agent-writable, so an agent can delete the record that would tell reviewers the plan is stale, or plant records naming any file. Count is unbounded (one entry per file across every run archive) and each file is read whole before parsing: a planted multi-GB file raises `MemoryError`, which the reader's `except (OSError, ValueError)` does not catch, so the checkpoint ends `failed-retryable (internal-error)` (`run._checkpoint`), a denial of the Draft PR for that run; a few thousand small records push the body past GitHub's 65,536-character limit with the same effect. Rendering: `_escape` covers `<`, `>`, `@` and `_printable` removes newlines, so no heading, HTML, mention or marker spoof is possible, but a repository path `[review passed](https://example.test)` renders as a link in the PR body because paths are not placed in code spans. Mitigating: the operator sees the authoritative "evidence may be stale" line on stdout at sync time, and the `branch_sync` ledger event records `overlap`/`stale_*` (also in the common directory, same trust level as the rest of the ledger).
- Fix: write the record under the operator state directory (`<state_dir>/branch-sync/stale/<sha256(feature)[:16]>/<event_id>.json`, same `_write_json`) and read it from there in `_stale_entries`; it is already keyed by feature, so continuations keep the source run's entries. Bound the read: skip files whose `st_size` exceeds a small cap (16 KiB is ample for 200 paths), keep at most the newest N entries (say 20) and say "and N more". Render each path as a code span with backticks removed from the path. Amend `data-model.md` § stale record accordingly.
- Test: in `test_draft_pr`'s stale tests, plant 500 records and one 100 MiB file and assert the section still renders with a bounded list and the checkpoint outcome is unchanged; plant a path `[x](https://e)` and assert it appears inside backticks; plant a record in the old common-directory location and assert it is ignored.

### Low

#### SEC-004: checkout-side ancestry answers trust replace refs, `info/grafts` and the commit-graph of the agent-writable `.git`

- Label: implementation bug (defense in depth for FR-001; the agent "influences" the check, AC-017, without gaining authority)
- Location: `branch_sync.py:603-607` (`checkout()` environment), `1006-1020` (`is_ancestor`, `merge_base`), `1372-1381` (`rev-list`)
- Evidence: reproduced in `/tmp/bsync-review-cg`: after `git replace --graft feat main`, `git merge-base --is-ancestor main feat` answers yes in the checkout, so `classify()` returns `up-to-date` for a branch that does not contain the base, and the agent then plans against a stale base, which is what #18 exists to prevent. `.git/info/grafts` gives the same answer (deprecated, still honored). `GIT_NO_REPLACE_OBJECTS=1` and `GIT_GRAFT_FILE=/dev/null` restore the truth. A forged `objects/info/commit-graph` (hash mismatch is not checked at load; `commit-graph verify` reports it) is loaded by both the checkout and the throwaway through the shared object directory, but `merge-tree`, `ls-tree` and `cat-file` take the tree from the commit object, so the replay cannot be steered; only walks (`rev-list`, `merge-base`) can be misled. The throwaway is immune to replace refs and grafts (own `GIT_DIR`). The agent gains no authority: the push stays bounded to the pinned feature branch, and feature-branch content is the agent's by design.
- Fix: in both runner environments add `GIT_NO_REPLACE_OBJECTS=1` and `GIT_GRAFT_FILE=/dev/null`; add `-c core.commitGraph=false` next to `NO_RECURSION` for the checkout and to `NO_MAINTENANCE` for the throwaway (one tuple each). Also validate every hash taken from Git output before it becomes an argument: `rev-list` lines and the `parent` header used for `--merge-base={original}` and `cat-file commit {original}` (`branch_sync.py:1384-1395`); a malformed commit object in the agent-writable store currently fails closed through a Git error, but the module's claim is that every name is validated data.
- Test: `test_replace_ref_does_not_hide_the_base`: `git replace --graft BRANCH main` in the scratch checkout, advance the base, assert `synchronized`, not `up-to-date`; a sibling with `info/grafts`; one asserting `core.commitGraph=false` appears in every logged argv (extend `test_runners_harden_every_command`).

#### SEC-005: the checkout's `objects/info/alternates` is honored by the throwaway

- Label: architecture issue (ADR-0005 lists `GIT_ALTERNATE_OBJECT_DIRECTORIES` among dropped variables but not the file; DEC-0007 refuses the comparable partial-clone shape)
- Location: `branch_sync.py:638-642` (`GIT_OBJECT_DIRECTORY=<common dir>/objects`), `789-800` (`shape()`)
- Evidence: reproduced: after the agent writes `/path/to/private/.git/objects` into the checkout's `objects/info/alternates`, `cat-file -e <blob>` in the throwaway finds an object of that private repository that it did not see before. Content under a known hash cannot be substituted, but `has()` probes answer for foreign objects and a `push` packs every object reachable from the replayed head that GitHub lacks: an agent whose sandbox cannot read a store the operator can read, and that knows an OID in it (commit hashes leak in logs, issues, shell history), can have the operator publish that object on the feature branch. In sandboxes that allow reads of the whole home directory the agent could copy the content into its branch anyway, so the gain is narrow.
- Fix: in `shape()`, when `<objects>/info/alternates` exists (`os.path.lexists`), block as `git-unavailable` with the detail "alternate object store" and one recovery, "clone the repository again without alternates, then rerun" (same shape as the partial-clone row; add it to the contract and policy tables so `test_every_cause_and_recovery_is_documented` keeps passing).
- Test: `EnvironmentRefusalTests.test_alternates_are_refused`: write the file, assert the block, assert no `ls-remote` or `fetch` ran (ARGV_LOG) and the snapshot is unchanged.

#### SEC-006: the throwaway command allow-list is an `assert`

- Label: implementation bug
- Location: `branch_sync.py:620` (`assert args[0] in THROWAWAY_COMMANDS`)
- Evidence: effective today because `tools/ballast:1032` and `launcher.py:306` execute `python -IS` (`-I` ignores `PYTHONOPTIMIZE`) and the tests run without `-O`; a future `-O`, or a reuse of the module from another entry point, removes the one guard behind guarantee 6 (nothing may gc, repack or prune the shared store).
- Fix: `if args[0] not in THROWAWAY_COMMANDS: raise ValueError(f"not a throwaway command: {args[0]}")` (same for the `self.bare is not None` assert, which guards against writing into no repository).
- Test: `FoundationTests.test_allow_list_survives_optimization`: run `python -O -I -S -c "import branch_sync; ..."` in a subprocess and assert the `ValueError` for `gc`.

### Informational (no change required)

- I-1: `GIT_EXEC_PATH`, `GIT_SSH_COMMAND`, `GIT_PROXY_COMMAND`, `GIT_TEMPLATE_DIR` (overridden by `--template=`) and `GIT_ATTR_SOURCE` (overridden by `--attr-source`) are inherited from the operator's environment. They are the operator's own, consistent with the model that keeps `GIT_CONFIG_GLOBAL`; only `GIT_EXEC_PATH` escapes the working-tree filter that `PATH` gets. Dropping it would make git fall back to its compiled-in exec path; worth a line in ADR-0005 either way.
- I-2: the checkout plumbing acts on whatever working tree the agent-writable `.git/config` `core.worktree` names. `status` and `read-tree -m -u` would then read and write there, but only a replica that already matches the index passes `dirty()`, and the launcher's recheck hashes the real root, so the agent can at most make the sync update a copy it already owns. `--work-tree=<root>` on checkout commands would remove the question; optional.
- I-3: `find_overlap` reads the run's ledger (`ledger.read`, common directory) to decide `stale_review`; it affects only the stale flags, never a block or a push.
- I-4: `_write_json` into `<common dir>/speckit-runs/<run>/branch-sync/` refuses a symlinked directory and a failed record turns a good outcome into `blocked`/`not recorded`: fail closed, as the contract says. Moot once SEC-003 moves the file.
- I-5: `LC_ALL=C` and English substring matching on `push` stderr (`stale info`, `[remote rejected]`) decide only `diverged` versus `push-failed` retryability, never whether anything is pushed.

## Verified without findings

- Program resolution refuses the checkout, temp roots and any directory below a `.git` entry, after resolving symlinks; `test_checkout_git_is_never_executed` and `test_git_only_in_the_checkout` cover it.
- The throwaway never reads the checkout's configuration; the credential helper, `insteadOf` rules and `sshCommand` can come only from the operator's global or system configuration (`test_checkout_configuration_never_runs` plants all of them and a `pre-push`/`reference-transaction` hook; none runs).
- No command in the throwaway is `gc`, `repack`, `prune`, `maintenance`, `fsck` or `commit-graph`; `fetch` runs with `maintenance.auto=false`, `gc.auto=0`, `fetch.writeCommitGraph=false` (`test_operator_gc_never_prunes_the_checkout`).
- The base branch and non-feature branches are never pushed, including through recovery (`test_fast_forward_record_never_pushes`, `test_run_on_the_base_branch_only_fast_forwards`, `test_only_feature_branches_are_rewritten`).
- Every push carries `--force-with-lease=refs/heads/B:<observed>` where `observed` is `COMMIT`-validated and comes from the same invocation's `ls-remote`/fetch or the operator-written record.
- Names and paths are shell-quoted in recovery text and stripped of control characters elsewhere; Git output is never printed or stored (`test_names_are_quoted_and_escaped`, `test_untrusted_names_are_printed_as_data`).
- Every HEAD change is followed by the protected-input recheck, and a crash after `update-ref` is caught by `launcher._refusal` (`test_crash_after_a_protected_update_is_caught_by_the_launcher`).

## Required before approval

1. SEC-001 fix and its regression test (blocking: a demonstrated run of an agent-configured program with operator authority).
2. SEC-002: pin the feature at `start` and read the Issue number from the pin on `resume`, with the test; or, at minimum, an explicit ADR-0005/contract statement that the rewrite rule's Issue number depends on the wrapper's run-state digest, with a test that an `inputs.json` edit during a step refuses the next invocation.
3. SEC-003: bound the read and code-span the paths (blocking for the denial-of-checkpoint); moving the record to operator state is recommended and small.
4. SEC-004, SEC-005, SEC-006: one-line hardenings each, with the listed tests; not individually blocking, but together they are what makes the "every name is data, nothing from the checkout decides" claim hold.

- Verdict: REVISE
