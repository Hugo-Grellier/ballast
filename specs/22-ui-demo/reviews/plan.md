## Where the plan needs work

The security boundary of the capture job. The plan reasons that dispatching on the default-branch ref keeps feature-branch edits of the workflow from running with the operator's authority, and that a secretless, `contents: read` job grants nothing new. But the job then checks out the PR head and runs its command, which executes code an agent wrote on the feature branch (package scripts, test fixtures, anything the command calls), in a run whose ref is the default branch, inside the same job as `actions/upload-artifact`. Code in a job can reach the runner's Actions runtime token used by later action steps (by reading the runner worker or rewriting the already-downloaded action files the next step executes), and that token writes Actions cache entries scoped to the run's ref, here the default branch. Default-branch caches are restored by every branch and by the project's privileged default-branch workflows. A feature-branch push or `pull_request` CI run cannot write that scope today, so this is new reach for agent-written code. Neither research R2's accepted consequence, R4, the constitution check (BL-INV-002, BL-INV-003) nor the proposed ADR-0012 rules address it. The plan needs a decided mitigation or an explicitly accepted, documented residual risk in ADR-0012 before implementation; it is an R2 security-boundary question.

The template's job timeout expression. `timeout-minutes: ${{ fromJSON(inputs.timeout_minutes) + 5 }}` relies on arithmetic, which GitHub Actions expressions do not support. The planned pyyaml static test would not detect it; the workflow would fail only when GitHub evaluates it.

The run-list window. R6 lists runs from "the earliest pending capture's date", but every scenario's newest event is re-resolved at each checkpoint (nothing is cached), and the list reads one page of 100 without pagination. A busy repository or an old capture can drop the matching run from the page and turn a real capture into `failed (run-not-found)` after 24 h.

A smaller presentation point: a demo command that itself exits 124 is reported as `timed-out`; this is acceptable but worth one line in the documentation.

## Verdict

Changes requested: the coverage, authority and packet design are sound, but the capture job's execution scope is an unaddressed R2 security boundary that needs a human decision before tasks are generated. The verdict and every disposition here are agent-provisional.

## Findings (recorded from the review draft)

- F-001 (high, architecture-issue, accepted-provisionally): Not acceptable to proceed on: the capture job runs PR-head code (agent-writable) in a run whose ref is the default branch, in the same job as actions/upload-artifact. Job code can obtain the runner's Actions runtime token (worker memory, or rewriting the downloaded action files the next step runs) and write default-branch-scoped Actions caches that every branch and privileged default-branch workflows restore; feature-branch CI cannot reach that scope today. Research R2 says this grants nothing new, and neither R4, the constitution check (BL-INV-002/003) nor ADR-0012 addresses it. A human must choose a mitigation (for example isolating the command from any action step and runtime token, or a non-default dispatch scope) or an explicitly accepted residual risk recorded in ADR-0012 and the docs.
- F-002 (medium, implementation-bug, accepted-provisionally): The template contract sets job timeout-minutes to fromJSON(inputs.timeout_minutes) + 5, but GitHub Actions expressions have no arithmetic operators, and the planned pyyaml static test cannot detect it. Can be fixed when the plan is revised for F-001 (for example a fixed 65-minute job timeout as the backstop, with the command's own timeout enforcing the contract value) and covered by the static test.
- F-003 (low, spec-ambiguity, open): R6 lists runs created since the earliest pending capture, yet every scenario's newest event is re-resolved at each checkpoint and the list reads one 100-run page without pagination; a busy repository or an old capture can lose its run and show failed (run-not-found) for a real capture. Define the window as the oldest newest-event date and paginate or bound it explicitly.
- F-004 (info, spec-ambiguity, open): A demo command that itself exits 124 (or is killed with 137) is reported as timed-out; acceptable, but the documentation should say so.

## Resolution

The plan was revised for every finding. The spec is unchanged here; [decisions.md DEC-0001](../decisions.md#dec-0001--proposal) records the FR-007 and AC-010 wording change that F-001 needs.

- **F-001**: the capture now runs on the **PR's head branch** ref, never the default branch. The PR-head code the job runs can reach the Actions runtime token, but that token can then write only the feature branch's cache scope, which only that branch's own runs restore. The definition GitHub loads from the branch is trusted by checking it. Before dispatching, Ballast requires the head commit's `ballast-demo.yml` to have the same blob ID as the default branch's (`refused (workflow-differs)` otherwise). On the runner, `GITHUB_SHA` must equal the requested commit. Afterwards, a run whose `head_sha` is not the requested commit is `failed (commit-mismatch)` and never linked. Splitting the job with `permissions: {}` was rejected: the runtime token and its cache scope follow the run's ref, not a job's permissions or actions, so the split would still leave default-branch caches writable. The template has exactly one job and no cache action. Where: [research R15](../research.md#r15-execution-scope-of-the-capture-run-plan-review-f-001) (new), R2, R9, R12 and R14; [plan](../plan.md) summary, constraints, constitution check rows 2 and 3, ADR-0012 rules and review notes; [capture-workflow.md](../contracts/capture-workflow.md); [demo-command.md](../contracts/demo-command.md); [data-model.md](../data-model.md); [quickstart](../quickstart.md) scenarios 1, 7, 21 and 22; [decisions.md DEC-0001](../decisions.md#dec-0001--proposal).
- **F-002**: the job's `timeout-minutes` is now the fixed literal `65`, a backstop only. The command's own `timeout --kill-after=30s "${TIMEOUT}m"` enforces the contract value (validated 1–60). The static test asserts the integer `65` with no expression, and checks the `timeout` invocation and its `env:` source. Where: [research R4](../research.md#r4-capture-workflow-template-templatesgithubworkflowsballast-demoyml); [capture-workflow.md](../contracts/capture-workflow.md) shape table and step 3; [demo-config.md](../contracts/demo-config.md) comment; [plan](../plan.md) constraints; [quickstart](../quickstart.md) scenario 7.
- **F-003**: the run-list window now starts at the UTC date of the **oldest** of the scenarios' newest events. The list is filtered to the feature branch, and is read in explicit pages of 100 until a short page, at most 5 pages. An unmatched request when the bound is hit is `failed (run-list-truncated)`, never `run-not-found` or a guess. Where: [research R6](../research.md#r6-outcome-resolution-at-a-checkpoint) and R3, R12; [capture-workflow.md](../contracts/capture-workflow.md) reads table; [data-model.md](../data-model.md) reasons; [plan](../plan.md) performance goals; [quickstart](../quickstart.md) scenario 23.
- **F-004**: exit 124 and 137 are documented: a command that itself exits 124 or 137, or is killed by the out-of-memory killer, is reported `timed-out`. Where: [research R5](../research.md#r5-failure-causes-without-downloading-logs); [capture-workflow.md](../contracts/capture-workflow.md) step 4; the policy subsection in the [plan](../plan.md) repository impact; [quickstart](../quickstart.md) scenario 8 (docs check).
