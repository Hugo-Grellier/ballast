# Research: Qualify one zero-cost provider fallback

Phase 0 decisions for [plan.md](plan.md). Every decision is agent-provisional (Autonomous run `f200c320`); merging the PR is the only human approval. Sources are the files named in [discovery.md](discovery.md) and the code read for this plan: `tools/spec_workflow/agent.py` (`main`, `_attempt`, `permission_args`, `_protected_state`), `autonomy.py` (`confined_argv`, `confined_env`, `codex_sandbox_nests`, `tree_digest`, `run_dir`, `append_step`, the record renderer), `artifacts.py` (review entry `cross_provider`, draft `agent.provider`), `ledger.py` (`ENUM_FIELDS`, `FIELDS`, `append`, `_semantic_problems`) and `run.py` (`main`, `_split_mode`, `_start_autonomous`, resume option parsing).

Host probes could not run while planning: this planning session had no approval to execute `codex` or `ollama` or to call the loopback endpoint. Everything that depends on the host is therefore a pilot task (R10) that runs first, and every design choice below fails closed if the pilot shows something different.

## R1. Candidate backend

- **Decision**: The Codex CLI in local-provider mode, `codex exec --oss --local-provider ollama -m MODEL`, against the host's Ollama server at its fixed default loopback endpoint `127.0.0.1:11434` (DEC-0003), with the model the operator names (the intake reports `qwen3:4b`, CPU-only).
- **Rationale**: It reuses the wrapper's existing Codex path: the same `permission_args("codex")` sandbox flags, `confined_argv` and `confined_env`, protected-state check, systemd scope and subreaper. It needs no account and no credential, and no repository content leaves the machine (D-01, D-03). It stays CLI-native (PRODUCT-SPEC 5.3), so the wrapper adds no direct-API harness.
- **Alternatives considered**:
  - *Claude Code pointed at Ollama's Anthropic-compatible endpoint* (`ANTHROPIC_BASE_URL`). Rejected: it redirects a CLI built for a paid provider by environment, needs an auth variable that `confined_env` removes on purpose, and its tool permission model would need a second qualification.
  - *A hosted free tier* (OpenRouter free models, Gemini CLI free tier, other hosted endpoints). Rejected by D-03: remote, account-bound, privacy terms and free status cannot be established at runtime; Issue #23 excludes account sign-up.
  - *LM Studio through `--local-provider lmstudio`*. Same path and adding it later is additive, but it is not installed on the operator host, so it cannot be piloted.
  - *Another agent CLI (aider, opencode) or a direct Ollama API harness*. Rejected: a new permission model to qualify, or the direct-API harness the spec lists as a non-goal.

## R2. Normalized failure causes

- **Decision**: A new pure function classifies one finished primary attempt into a fixed cause set. Recoverable: `quota-exhausted`, `provider-unavailable`, `cli-unavailable`. Non-recoverable: `success`, `blocked` (`EXIT_BLOCKED`), `tampered` (`EXIT_TAMPERED`), `limit` (`EXIT_LIMIT` or the wall-time timeout), `interrupted` (`EXIT_INTERRUPTED`), `draft-refused`, `unrecognized`. A cause is recoverable only when the exit code is nonzero and none of the reserved wrapper codes, no blocking status was reported, every process was contained, and the last 64 KiB of the attempt's stderr and stdout match one of a fixed per-integration signature table (usage-limit and rate-limit messages for `quota-exhausted`; connection, DNS, TLS, 5xx and "stream disconnected" messages for `provider-unavailable`). `cli-unavailable` is the primary CLI missing from `PATH` (`_real_executable` raising), detected before the primary runs: that primary attempt is recorded as not run and counts no agent step.
- **Rationale**: FR-002 requires a fixed set and treats anything unknown as non-recoverable. Matching the tail of the output, not the whole stream, keeps an agent's quoted text earlier in the session from matching. A primary agent that prints a signature on purpose gains nothing: eligibility still requires an unchanged state (R3), and the fallback has no more authority than the primary (R6).
- **Alternatives considered**: Exit codes alone (both CLIs use 1 for most failures, so quota cannot be told apart). Parsing `claude --output-format json` (Spec Kit owns the primary argv; changing it changes what Spec Kit records). The signature strings are pinned from the pilot's captured messages (R10) and kept as test fixtures with account details removed.
- **Signature sources**: messages captured in the pilot (R10), the CLIs' own source or documentation, and the logs of earlier runs on the host, each redacted. A cause with no signature for an integration stays `unrecognized` for that integration, so it fails closed. It is listed in `evaluation.md`. When no quota signature exists for any integration, it is recorded as a discovery in `decisions.md`, because AC-001 could then never be met on a real run.

## R3. Evidence that the primary attempt changed nothing

- **Decision** (DEC-0001): Eligible only when every piece of the following evidence is equal before and after the failed attempt:
  - `autonomy.tree_digest`: tracked and untracked, non-ignored files. Protected inputs, the feature's `reviews/` and `autonomous/drafts/` are excluded, as today.
  - `autonomy.reviews_digest`.
  - No draft was created.
  - A new `autonomy.ignored_digest(root)`: every git-ignored path in the worktree, found with `git ls-files -z --others --ignored --exclude-standard --directory`. Collapsed directories are walked without following links. The protected inputs are excluded, because a change there is already `tampered`, except the Spec Kit paths agents may write inside `.specify/` (`SPECIFY_WRITABLE`). The wrapper's own log files are excluded too. Each entry contributes its relative path, type, mode, size, `mtime_ns`, `ctime_ns`, inode and link target from `lstat`. A process cannot set `ctime`, so any write, chmod, rename or creation changes the digest without reading file contents.
  - A new `autonomy.refs_digest(root)`: `HEAD` (resolved, or the symbolic ref) and the SHA-256 of `git for-each-ref --format='%(refname) %(objectname)'`, so a commit, branch or tag the primary made counts as a change even when the working tree matches.

  The protected-state digests must also be equal, as today; a difference is `tampered`, which is not recoverable.

  The before values are taken only when the fallback setting is on, in both modes, so a disabled run does exactly what it does today. When any piece cannot be established, the state cannot be checked and the fallback is refused as `changed-state` with the detail `worktree state could not be checked`. That covers a Git failure, an entry that cannot be `lstat`ed, more than 200,000 ignored entries, or more than 10 s for the ignored walk. Any difference also refuses with `changed-state` (AC-009).
- **Scope**: AC-009's state is the worktree, the drafts and the protected state. Writes outside the worktree are not replayed state: an Autonomous attempt's private temporary directory is discarded, and the fallback gets a fresh one and a fresh private `CODEX_HOME` (R6).
- **Rationale**: D-04 picks evidence over a list of step types. The tree, reviews and protected digests are the ones the wrapper and recorders already trust. The ignored-path and ref digests close the gap that plan review and analyze F2 found, so the spec's promise holds as written (DEC-0001). Metadata hashing keeps the extra cost to one `lstat` walk per step while the setting is on.
- **Cost**: Every step pays for the walk while the setting is on, and a worktree with a very large ignored tree (for example a dependency cache over the entry cap) always refuses. Both are accepted: a refusal is only a missed fallback, never replayed state.

## R4. Operator opt-in and exit path

- **Decision**: `ballast run start --local-fallback MODEL` for human-gated and Autonomous starts, refused with `--mode chat`. `ballast run resume RUN --local-fallback MODEL|off` changes it for a later invocation. The launcher writes the setting to `fallback.json` in the run's operator directory (`autonomy.run_dir`, under `$XDG_STATE_HOME`, outside every agent's write authority, already used for both workflows). There is no endpoint option and no endpoint field (DEC-0003 option 1, plan-review F-001). The fallback talks only to Ollama's default endpoint `http://127.0.0.1:11434`, a constant of `fallback.py` (`OLLAMA_ENDPOINT`). Codex's built-in `ollama` provider cannot be pointed elsewhere by `--config` (it refuses `model_providers.ollama.*`, pilot item 2), so the probes and Codex use the same fixed endpoint and a probe can never check a server Codex will not use. The model must match the ledger `MODEL` pattern, must not start with `-`, and must not name a cloud tag. Off is the default and the exit path: start without the flag, or resume with `off`. Nothing is committed and nothing is installed beyond the code.
- **Rationale**: D-05 puts the setting outside agent reach and per host. `run_dir` exists for human-gated runs too, and the wrapper already reads operator state from there. One file serves both modes, so there is no second copy. Autonomous `record.md` and every fallback step entry and ledger event show whether the setting was on (AC-020). A human-gated run has no `record.md` (plan-review F-004). Its run record is the operator directory's `fallback.json`, which the launcher alone writes and keeps after `off`. `ballast run status RUN` prints it as a `Local fallback:` line whenever the file exists, and each step's `meta.json` carries `local_fallback: true` while the setting is on. The ledger `route` events of every step that considered the fallback complete the record. With no `fallback.json`, nothing new is printed or written.
- **Alternatives considered**: A `ballast.toml` section (commits a host-specific setting; still possible later, additive). An environment variable (an agent step's environment is inherited by its children, and nothing would record it). A field in the Autonomous `record.json` (human-gated runs have no record).

## R5. Eligibility probes before any content is sent

- **Decision**: The wrapper runs these checks in order, after the primary attempt and before counting or starting the fallback. The first failure refuses with its reason, and none of them sends a prompt or repository content:
  1. setting present and valid (else no fallback, no record);
  2. headless step of a human-gated or Autonomous run (a Chat record means no fallback, D-08);
  3. cause recoverable (R2), else no fallback;
  4. state unchanged (R3), else `changed-state`;
  5. the endpoint is the fixed `OLLAMA_ENDPOINT` (a loopback literal), the probes use only it, and the built environment holds none of `CODEX_OSS_BASE_URL`, `CODEX_OSS_PORT` and `OLLAMA_HOST`, else `privacy-exclusion` (defense in depth: the wrapper strips them, so a hit means the build is wrong);
  6. `GET /api/version` answers within 5 s and reports at least `MIN_OLLAMA_VERSION` 0.13.4, the minimum Codex 0.155.1 requires (pilot items 4 and 9, DEC-0003), else `incompatible-capability` (`server not answering`, `ollama older than 0.13.4`, or `ollama version unknown` when the version cannot be parsed);
  7. `GET /api/tags` lists the model by exact name with a nonzero size and digest, else `unknown-free-status`;
  8. that entry and `POST /api/show {"model": MODEL}` carry no `remote_host` or `remote_model` and the name has no `cloud` tag, else `privacy-exclusion`;
  9. a trusted `codex` (`autonomy.trusted_program`) whose `codex exec --help` lists `--oss` and `--local-provider`, and, when the prompt names a Spec Kit command, the project's Codex skill for it (`.agents/skills/<command>/SKILL.md`, a regular file inside the worktree, at the path the pilot confirms) exists, else `incompatible-capability`. A project with only the Claude integration installed has no such skill, so the fallback would only use an agent step and fail its postconditions (plan-review PD-0010 F-001);
  10. Codex's sandbox starts under the confinement the step would use: `autonomy.codex_sandbox_nests` for an Autonomous step, the same `codex sandbox` probe without bubblewrap for a human-gated step, else `incompatible-capability`;
  11. no Codex configuration layer outside the fallback's private `CODEX_HOME` exists among those the pilot found Codex reads (R6), and the user skills directory `~/.agents/skills` of the operator's home is absent or empty (R6, plan-review F-003), else `permission-mismatch`;
  11a. `POST /api/show` `parameters` carries `num_ctx` of at least `MIN_SERVED_CONTEXT` (16384), else `incompatible-capability` (`served context below 16384`, or `served context unknown` when absent). Codex sends about 12k input tokens for a trivial prompt (pilot item 10), and a server default of 4096 rejects every request (DEC-0004). The qualified candidate is therefore a local variant such as `qwen3:4b-16k` (`FROM qwen3:4b`, `PARAMETER num_ctx 16384`), not the stock tag;
  12. the built fallback argv and environment pass the exact-argv comparison (R6), else `permission-mismatch`;
  13. for an Autonomous run, `_autonomous_run` counts the step: an exhausted limit stops the run with the existing limit refusal (AC-015).
- **Deadline**: Checks 5 to 11 and 11a share one 10 s budget (the plan's performance goal). When it runs out, the fallback is refused as `incompatible-capability` with the detail `eligibility checks timed out`.
- **Rationale**: D-07: probes only refuse. No model list ships (FR-009). Each probe sends only the model name to the loopback server. HTTP uses `urllib.request` with an opener that has no proxy handler, so `http_proxy` cannot redirect the probe. The order puts the cheap, local checks first and the subprocess probes last.
- **Known gap**: Codex in `--oss` mode pulls a missing model. Check 7 makes this unreachable unless the model is removed between the probe and the run. That race costs a download, never repository content, and is recorded as residual risk.

## R6. Fallback invocation and the permission comparison

- **Decision**: The fallback is a Codex attempt built from scratch: `permission_args("codex", ["exec", prompt])` plus exactly `--oss`, `--local-provider ollama`, `-m MODEL` and `--json`. No base-URL key appears in the argv: Codex refuses any `-c model_providers.ollama.*` and ignores `oss_base_url` (pilot item 2, DEC-0003), so the fixed default endpoint is what Codex uses and what R5 probes. The primary's extra arguments (`args[2:]`, the primary integration's flags) are never forwarded. A Claude prompt `/speckit-x …` becomes `$speckit-x …`, the form Spec Kit's Codex integration uses. Environment: `confined_env(env, None)` (no provider key kept, stricter than a primary Codex step), with `OLLAMA_HOST`, `CODEX_OSS_BASE_URL` and `CODEX_OSS_PORT` removed and `CODEX_HOME` set to the private directory below. An Autonomous step uses the same `confined_argv` call as its primary. A human-gated step uses the same unconfined argv shape as a human-gated primary: systemd scope plus Codex's sandbox. `permission_mismatch(argv, env, codex_home, *, codex, prompt, model)` is an exact allowlist, not a denylist (plan-review F-002): the inner Codex argv (before `confined_argv` or the systemd scope wraps it) must equal, token for token and in order, the one list `fallback_argv(codex, prompt, model)` builds, which is the canonical headless Codex profile (`permission_args("codex", ["exec", prompt])`: sandbox `workspace-write`, `network_access=false`, `writable_roots=[]`) plus the five fixed tokens above. Any added, removed, reordered or changed token refuses, so a widening flag needs no entry to be caught. The pilot found these `codex exec` flags outside the profile, and each is a test case: `--approve-for-me`, `--enable`/`--disable FEATURE`, `--worktree`, `--ignore-user-config`, `-p`/`--profile`, `--ignore-rules`, `--strict-config`, `--add-dir`, `--sandbox`, `--dangerously-bypass-approvals-and-sandbox`, `--dangerously-bypass-hook-trust`, any `-c`/`--config` key, and a second `--oss`, `-m` or `--local-provider`. The environment must equal `fallback_env` output: only `confined_env` names plus `CODEX_HOME` set to the private path, and none of `CODEX_OSS_BASE_URL`, `CODEX_OSS_PORT`, `OLLAMA_HOST`. Any difference refuses.
- **Codex configuration (plan-review F-001)**: The comparison above sees only argv and environment, but Codex also reads its configuration files. The user's `$CODEX_HOME/config.toml` can add `mcp_servers`, a `notify` program or a default `profile`/`profiles`, which a Claude primary never has (`--strict-mcp-config`, project-only settings). The fallback therefore runs with `CODEX_HOME` set to a fresh directory inside the attempt's private directory (mode 0700, removed afterwards), created by the wrapper and holding no `config.toml`. That pins `mcp_servers` and `profiles` empty, `notify` unset and no default profile, and no user configuration file is read. `--oss` needs no login, so no credential is copied in; the pilot confirms this. Under bubblewrap, that directory is the Codex home the confinement exposes, through the existing agent-home overlay. The pilot (R10) lists every other layer Codex reads, such as a system file or a project `.codex/config.toml`. Check 11 of R5 refuses with `permission-mismatch` when any of them exists, or when the pilot could not establish the list. `CODEX_HOME` is the one environment variable the comparison allows beyond `confined_env`, and only with the wrapper's private path.
- **User skills (plan-review F-003)**: Codex also loads skills from `~/.agents/skills`, outside `CODEX_HOME` (pilot items 5 and 6). Skills are instructions, not tools or sandbox settings, so they do not widen the sandbox, but they would make the fallback's context differ from the canonical headless Codex step's, and "no user configuration is read" would be untrue. The smaller safe option is to refuse, not to rewrite `HOME` (a scratch `HOME` would also move the Git, bubblewrap overlay and systemd user paths the step depends on, which needs its own pilot). Check 11 therefore refuses with `permission-mismatch` (detail `user skills directory is not empty`) when `~/.agents/skills`, in the operator's home, exists and is not an empty directory, or is a symlink or cannot be read. The check looks at the operator's real home in both modes. It is conservative for an Autonomous step: the agent-home overlays (`autonomy.agent_homes`) cover only the Claude and Codex homes and `~/.cache`, so the plan does not assume bubblewrap hides this directory. The project's own `.agents/skills` (the Spec Kit skills of check 9) and `AGENTS.md` are project content a primary Codex step loads too, so they stay. The cost is a missed fallback for an operator who keeps personal skills there; they empty the directory or leave the fallback off.
- **Rationale**: FR-005 and D-02. The comparison is an explicit invariant check at run time: it catches drift between the argv the wrapper builds and the one it launches. It cannot catch a widening inside `permission_args` or `fallback_argv` themselves, because it compares against them; a test that pins the literal fallback token list (`workspace-write`, `network_access=false`, `writable_roots=[]` and the five fixed tokens) catches that, so a later change to `permission_args` or a Codex flag rename cannot widen the fallback silently (plan-review PD-0013 F-002). Dropping `args[2:]` means no primary-integration flag reaches Codex. Stripping the endpoint variables, using the fixed default endpoint and reading no user `config.toml` at all means nothing the operator or an earlier step configured can point the provider elsewhere or add a tool.
- **Alternatives considered**: Reusing the primary argv with flags appended (would forward Claude flags to Codex). Loosening either sandbox when Codex does not nest (forbidden by D-02 and BL-INV-003).

## R7. Usage evidence

- **Decision**: The fallback runs `codex exec --json`. The wrapper parses the JSON Lines: the text of `agent_message` items is the stdout used for `RECONCILE_STATUS` detection and is what the terminal shows; the summed `turn.completed` `usage` (input, cached and output tokens) is written to `usage.json` in the step's log directory and recorded as one ledger `usage` event, source `client-counter`, `counter_source` `codex-exec-json`, with the SHA-256 of that file as `counter_digest`. `complete` is true only when every turn reported usage and the process exited by itself. When the stream cannot be parsed, the attempt is a `mechanical-failure` and no usage is recorded. A Claude or Codex primary attempt records no usage, as today.
- **Rationale**: AC-011 asks for usage when the backend reports it, and `--json` is how this backend reports it. Failing closed on an unparsable stream keeps a `BLOCKED_*` status from being missed. Spec Kit records only the exit code, so the stdout format change is invisible to it.
- **Consequence**: Ledger usage totals for a run with a fallback stay unavailable, because the failed primary attempt has no counter. That is the ledger's existing rule (no invented values).

## R8. Ledger and step records

- **Decision**: Additive only, `schema_version` stays 1. `route` gains `route_source` value `fallback`, `outcome` values unchanged, and three optional fields: `failure_cause` (label, the R2 set), `fallback` (`selected` or `refused`) and `fallback_reason` (`unknown-free-status`, `privacy-exclusion`, `incompatible-capability`, `permission-mismatch`, `changed-state`). The wrapper appends with source `runner`: one `route` for the failed primary (provider = primary integration, `route_source` `operator-choice`, `attempt` n, `failure_cause`, `fallback` and `fallback_reason` when refused), one `route` for the fallback (provider `ollama`, model, `route_source` `fallback`, `attempt` n+1, outcome) and its `usage`. `stage` is the command label, `cause_id` the primary step's ID (its log directory name), and `event_id` is `fallback:<step>:<attempt>:<kind>`. `ledger.append` is idempotent per event ID, so a repeated write adds nothing (AC-014). Nothing is written when the setting is off or the primary did not fail recoverably. An Autonomous `steps.jsonl` entry gains `failure_cause` and `fallback {decision, reason}` on the primary, and `route: "fallback"`, `provider: "ollama"`, `model`, `local_fallback: true` on the fallback.
- **Rationale**: FR-007; the ledger's precedents (`pull_request`, `branch_sync`, `mode`) add enumerations and optional fields without bumping the version. No field holds account, quota or credential data, or free text (AC-017).
- **Review provenance (AC-016)**: `artifacts.py` sets `cross_provider` false and records `provider` `ollama` and the runner-known model for a draft from a fallback step, ignoring any model the agent reports. Today `cross_provider` is `integration != run integration`, which would wrongly be true for a Codex fallback in a Claude-authored run. A human-gated run has no step records or recorder. Its reviews reach the ledger as `review` events that the reviewing agent or the operator records, so a fallback model could name another provider. The trusted evidence there is the wrapper's runner `route` event with `route_source: fallback` on the review step's stage, which is a `ballast-review` command, the role rule `_role` already uses. `ledger.report` therefore never counts a review as cross-provider in a run holding a successful fallback `route` on a review stage (analyze C1). The rule is conservative, run-wide: it may under-count a genuine cross-provider review in that run, but it never over-claims.

## R9. Bounds

- **Decision** (DEC-0001): At most one fallback per step invocation. It comes only after the step's first primary attempt (attempt 1, with no draft refused before it) failed for a recoverable cause. A primary that fails on a draft-retry attempt (attempt 2 or later) never falls back. It ends as today, with its `failure_cause` recorded when the setting is on. A fallback attempt is never followed by a draft retry or another fallback, whether it fails, is blocked, times out or has its draft refused (D-06, AC-013). A step that falls back therefore makes exactly two attempts: one primary and one fallback (SC-005, FR-006). A step that never considers the fallback keeps the existing draft-retry loop, which this feature does not change. The fallback is an agent step under `max_agent_steps` in an Autonomous run (AC-015). A human-gated run has no step limit, so it is bounded by the single fallback attempt and its timeout. The timeout is the Autonomous remaining wall time, or 3600 s for a human-gated step, so an unresponsive CPU model cannot hold a human-gated run forever. A timeout records `incomplete`.
- **Rationale**: SC-005 and FR-006 as written. The draft-retry loop and the fallback never combine on one step, so neither bound depends on the other, and the existing limits stay authoritative.

## R10. Pilot on the operator host (first implementation task)

- **Decision**: Before any wrapper change, the pilot runs on the qualified host and records results in `specs/23-free-fallback/evaluation.md`:
  1. versions of `codex` and `ollama`; `codex exec --help` shows `--oss`, `--local-provider`, `--json`; the `--config` key for the Ollama base URL (done: none exists, DEC-0003, so the endpoint is fixed); `/api/tags` and `/api/show` fields for a local and a cloud tag;
  2. `codex sandbox` nesting inside Ballast's bubblewrap (`codex_sandbox_nests`) and without it;
  3. one real `codex exec --oss --local-provider ollama -m qwen3:4b --json` run of a small Spec Kit step in a scratch project under the wrapper's confinement, with duration, `--json` event shape and usage;
  4. captured, redacted quota and unavailability messages from both CLIs, to pin R2's signatures.
  5. the Codex configuration layers `codex exec --oss` reads (user, system, project), and a run with an empty private `CODEX_HOME` (R6);
  6. the project path where Codex finds a Spec Kit skill for a `$speckit-x` prompt (R5 check 9).

  The sandbox probes of item 2 and the layer check of item 5 run from the operator's own terminal, not from inside a confined agent step, because nested confinement can change the result. `evaluation.md` says which context each result came from.
- **Known risk**: This run already recorded that Codex's sandbox does not start inside Ballast's confinement on this host (DEC-0004 in [record.md](autonomous/record.md)). The expected pilot result is therefore: Autonomous steps refuse the fallback as `incompatible-capability`, and human-gated steps may run it. A 4B CPU model may also be too weak or too slow to satisfy a step's postconditions. Either outcome is acceptable under SC-004 ("completes or is refused with a recorded cause"). A pilot that rejects the candidate outright, for example because `--oss` is missing or the model cannot finish any step, is recorded in `decisions.md` as a discovery. It never leads to a silent switch of backend.
