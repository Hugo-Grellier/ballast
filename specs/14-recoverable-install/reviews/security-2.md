## Threat model used

An agent can write every path in the checkout, including `.ballast/setup/` (stage, previous, kept), `.ballast/.setup-version`, `.gitignore`, `ballast.toml` and run state, and `/tmp`-class roots, between runs or from a surviving process. It cannot write operator state (`$XDG_STATE_HOME/ballast/<key>/`) or the cache (`$XDG_DATA_HOME/ballast/standard/`). The questions are whether planted checkout content can be restored, reused or executed under operator authority, whether the new locks or records let the launcher skip a check, and whether the operator's terminal can be driven.

## What was examined and holds

1. **Reuse is hash-gated with no fallback.** `copy_kept` and `copy_from_primary` both go through `copy_verified`, which copies into the stage and accepts the copy only when `installed_digests(stage)` equals the record (`kept-installation.json` in this checkout's operator state; the primary's `installation.json` in its own `state_dir`, valid only while its fingerprint equals the primary's stamp). A mismatch removes the copied entries and falls back to a full build. Links are copied as links (`symlinks=True`, `readlink`) and hashed as `link:<target>`, so a planted link cannot pass as a file. The record omits file modes (see SEC2-005 note), which matches the pre-existing trust baseline format.
2. **Journal and records are not forgeable.** `setup-attempt.json`, `installation.json`, `kept-installation.json`, `setup-holder.json` and `checkout.lock` live in `launcher.state_dir`, which refuses the checkout and agent temp roots; setup refuses when it is unavailable. `recover` validates `schema`, `phase`, `before` and `work` (`ATTEMPT` regex, so the work area is always `.ballast/setup/<16 hex>`); `roll_back` and `live_entries` apply `_safe` to every entry name. The attempt ID is `secrets.token_hex(8)` and `discard_work` clears every non-kept work area before an attempt, so content planted under `.ballast/setup/` can never be matched to a future `previous/`.
3. **Rollback cannot silently restore planted content.** `roll_back` moves `previous/<e>` back by rename, then compares the live installation with the journal's `before` digests and fails loudly (`roll back failed … differs … at <path>`, exit 1) instead of claiming success; the journal is removed so the next setup rebuilds, and the launcher's trust comparison still gates `BASES`. Content outside `BASES` (skills, policies) is content the agent could write directly at any time, so no authority is gained.
4. **Link safety.** `check_links` refuses a link at any ancestor of `PARENTS` and of every planned entry before staging and again before switching; renames move leaves, never through a link; `discard_work`, `finish` and the kept replacement delete through `launcher._remove_tree` (`O_NOFOLLOW` per parent, `rmtree` with `dir_fd`) or `unlink` a link; the constitution is created with `O_EXCL | O_NOFOLLOW` only when absent. `test_linked_work_area_is_refused` covers the work-area case. The remaining check-to-rename window is the first review's SEC-004 and is accepted here for the same reasons.
5. **Checkout lock.** `flock` on `checkout.lock` in operator state, `O_NOFOLLOW | O_CREAT`; setup `LOCK_EX`, launcher `LOCK_SH` via `_hold` before any journal read, made inheritable only after the `O_CLOEXEC` open so it survives `execv` and dies with the workflow tool; `subprocess` closes it for agents. The lock only adds refusals: `trust` and `discard-runs` refuse while setup holds it or a journal exists (F-005); `status --json` takes no lock and writes nothing. A dead holder's lock is released by the kernel (tests kill holders). The holder file is read as data and only after the lock is busy. No path lets a lock state skip the tamper marker, `in-progress` or baseline checks: `_refusal` still runs after `_hold`.
6. **Cache.** `fetch` extracts into `.fetch-<ref>+<random>` under `.locks/<ref>.lock`, writes `.ballast-cache.json` (digest, link target and executable bit of every file) and publishes with one rename; `damage` compares the tree with the record (missing record is damage); `ensure_standard` verifies before `setup` and `preview` and refetches under the lock from `ARCHIVE.format(repository=REPOSITORY, …)` only. `REF` (`[A-Za-z0-9][A-Za-z0-9._-]{0,99}`, no `..`) bounds the lock name, directory name and URL, and excludes `+`, so stale-extraction cleanup never touches another version. `tarfile.extractall(filter="data")` as on main.
7. **`ballast preview`.** The ref is `REF`-validated and cannot start with `-`, so neither argparse nor Git sees an option. The target's own `tools/setup` runs from the verified cache under `/usr/bin/python3 -I -S` with `cwd=work` (SEC-001 fix confirmed at `disposable_build`), `XDG_STATE_HOME` inside the disposable directory and `BALLAST_STANDARD_DIR` removed; the checkout contributes only `ballast.toml`, `.gitignore` and the constitution as data. Nothing is executed from the checkout; in the checkout only read-only Git commands run (`check-ignore --no-index`, `ls-files`, `rev-parse`). The disposable directory is removed in every outcome. `test_refusals_change_nothing` and the snapshot assertions hold.
8. **Trust model.** `BASES`, `SKIPPED` and the baseline format are unchanged; `.ballast/setup/` is outside `BASES`; `tools/setup` never references `trusted.json` and only reads `in-progress` (grep). Setup never edits `ballast.toml`. `ballast trust` stays the operator's command; the only baseline writer is `launcher._trust` (#55 untouched).
9. **Removal scope is narrower than main.** `main` deleted `INSTALLED`, shipped policy names and `SKILLS` matches unconditionally; this change removes only entries the project's ignore rules ignore (`git check-ignore --no-index`). See SEC2-004 for the one case where that is still too wide.

## Residual risks (concur with the first review)

SEC-003 (an older setup run while a journal is pending), SEC-004 (link swap between check and rename by a surviving process) and SEC-005 (the operator's environment reaches a previewed, unpinned version) are accepted for the reasons given there. One addition to SEC-004: a surviving process writing into the stage during the build gets its content recorded in `installation.json` and switched live; the trust baseline still gates `BASES`, and the paths outside `BASES` are ones the agent can write directly, so the record must not be read as an authority (SEC2-005).

SEC2-001, SEC2-002 and SEC2-003 (small, local changes with regression tests). SEC2-004 may be fixed now or tracked as a follow-up with the operator's agreement; SEC2-005 to SEC2-009 are accepted or informational and listed for the merge review.
