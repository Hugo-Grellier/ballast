# Testing: Ballast specifics

- Before `ballast trust`, install the group used by local CLI tests with `uv sync --locked --group spec-kit`, so later test runs do not change the protected `.venv`.
- Fast gate: `uv run --locked ruff check`, `uv run --locked ruff format --check`, and `uv run --locked --group spec-kit python -m unittest tests/test_*.py` (Python from `.python-version`). CI runs the same; `--locked` fails when `uv.lock` is out of date.
- Some tests skip in CI because they need a systemd user session, `bwrap` with user namespaces or the Codex sandbox; among them are the real-confinement tests of Autonomous and Chat steps. CI installs the locked Spec Kit CLI group, so CLI-dependent tests run there. Run the suite on a machine with the remaining prerequisites before a release and for any change to `tools/spec_workflow/agent.py`, `launcher.py` or the workflow file.
- Critical evidence: a step that changes a protected input fails (including `ballast.toml`); the launcher refuses before trust, after a tamper marker and after an unfinished step; `ballast` never runs a launcher from the checkout, only `setup` and `preview` download, and a cached version is verified against its content record before use; `tools/setup` refuses unignored installed paths, keeps run state and the constitution across a reinstall, and leaves the complete previous installation after any failure or kill (fault injection in `tests/test_setup.py`); `ballast preview` changes nothing but the cache; every relative link in installed documents resolves.
- A change to `tools/setup` or `tools/ballast` also needs an end-to-end run on a scratch project: `ballast setup`, `ballast trust`, `ballast ledger report`, and a clean `git status` apart from the project's own files.
