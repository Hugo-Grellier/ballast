# Issue tracker: GitHub

GitHub Issues are the work tracker and discussion surface. Read the issue, comments, labels and dependencies before work. Use `gh` from the checkout when GitHub access is available. PRs are for review, not the initial request surface. Accepted product and technical documents plus feature-local Spec Kit artifacts remain the authority for requirements.

Small bugs and narrow technical work may be fully specified in the issue, with acceptance criteria there. Investigations can start as issues with durable findings under `docs/research/` when useful. Significant new features use repository-local Spec Kit artifacts in `specs/<number>-<slug>/`; the issue links the spec and tracks status, dependencies and discussion. Accepted feature intent, behavior, plan, tasks and decisions live in that directory. Do not rewrite completed issues into specs. The [Spec Kit workflow](spec-kit-workflow.md) describes the stages and controlled one-way Issue updates.

Apply the [scope and decomposition gate](spec-kit-workflow.md#scope-and-decomposition-gate) before `speckit.specify`: a Milestone is a planned release target, an Epic/parent Issue coordinates a roadmap capability, and a feature Issue owns one independently specifiable outcome. `ready-for-agent` dispatches an actionable leaf Issue that passed this gate, whether a feature or a bounded small fix. It requires explicit acceptance criteria, known dependencies, resolved blocking product questions, initial R0/R1/R2 risk and relevant links. An unresolved Epic is a coordination object, never an implementation dispatch. A plan is **not** required before dispatch; planning follows. Use `needs-info` for blocking questions and `ready-for-human` for an explicit human decision. See [triage labels](triage-labels.md); use a Project field for transient stages if an existing Project makes that simple, instead of inventing labels.

Use the [feature-intake skill](../../.agents/skills/ballast-feature-intake/SKILL.md) for chat requests such as `Start #N`, `Fix #N`, `Investigate #N`, and `Continue #N`. It reads the Issue and relationships, asks for a genuine decomposition or scope decision, then uses `ballast intake`, which runs the pinned standard's helper after the trust check, for bounded, retryable GitHub setup. The helper's JSON result distinguishes completed from pending steps after a failure. Inspect the live Issue before retrying with the same parent and child slug. It does not alter Project membership; configured auto-add handles that.

For Epic children or substantial feature sub-issues, use GitHub issue dependencies when available; otherwise write `Blocked by: #...`. Work only on unblocked leaf tickets. Keep fine-grained implementation in `tasks.md`; do not export every task to a GitHub Issue. Update GitHub from accepted repository artifacts with concise status and links, never copy Issue edits back into an approved spec automatically. When a skill says "publish to the issue tracker," create an issue; when it says "fetch the relevant ticket," read the issue and comments.
