# Agent Run Ledger schema v1

The ledger is `events.jsonl` under the Git common directory's `speckit-runs/<run-id>/`. It is local to the clone, outside every worktree and Git tracking. Removing a worktree does not remove it. Each line is one object with exactly `schema_version`, `run_id`, `feature`, `sequence`, `observed_at`, `event_id`, `kind`, `source`, and `data`. `schema_version` is `1`. Sequence starts at 1 and increases by one. Event IDs are unique per run; imported runner IDs use the source log line number so retry is idempotent. A conflicting duplicate, unknown field, malformed line, or unsupported version invalidates the stream; reading never repairs it.

`data` uses the fixed per-kind field allowlist in `ledger.py` (`FIELDS`). Kinds are `run`, `step`, `gate`, `route`, `classifier`, `escalation`, `review`, `finding`, `verification`, `convergence`, `usage`, `human_action`, `snapshot`, `pull_request`, `branch_sync`, and `acceptance_packet`. Sources are `runner`, `client-counter`, `operator-attested`, and `agent-reported`. The source label records provenance, not an attestation that a local process cannot be forged. An `agent-reported` identity alone cannot establish independent review, actual model, or human action. `usage` requires a `client-counter` source, a bounded source label, a SHA-256 digest of the client counter artifact, and complete non-overlapping invocation scopes to contribute to totals. A digest makes the claim auditable; it does not authenticate who submitted it.

The launcher records the runner snapshot at invocation end. Its local archive also stores `invocation.json` with only the exit status and ending log-line count. If that status is 130 while a gate is waiting, a state value of `reject` is recorded as `unobserved`: Spec Kit can produce that value on Ctrl-C without a human rejection. A manual `ledger.py import` can use the archived status to recover this distinction, but does not claim to have observed the invocation-end tree; use `snapshot` for a separate operator observation.

The schema accepts IDs, bounded labels, nonnegative counters, booleans, and digests only. Status, verdict, severity, resolution, route source, profile, effort, and action fields use the fixed enumerations in `ledger.py` (`ENUM_FIELDS`); unrecognized spellings fail validation. It has no free-form message, command argument, prompt, stdout/stderr, raw review prose, secret, account, quota, or campaign-content field. Raw agent logs retain the existing local-only handling. `run` and `step` observations come from the archived Spec Kit log and state snapshot. Gate choice is captured only from that invocation's final state, then attached to its last newly imported gate occurrence. A choice skipped before resume remains unavailable. The importer also records a runner snapshot at invocation end; a later changed tree or feature digest makes earlier final acceptance stale even when the worktree is subsequently removed.

Review and convergence observations bind to the implementation tree plus current spec, intent, plan, tasks, and manifest digests. `alternate_available` belongs to a specific `review_id`; the report distinguishes it from actual cross-provider use. A rejected plan gate requires a changed plan/spec, passing verification, an independent approved review bound to those digests, and a manual recovery action before later approval counts as compliant. A rejected tasks gate requires changed tasks, a passing `speckit-analyze` check, and manual recovery. Agent-reported checks or convergence do not prove compliance. Once the worktree is removed, current compliance and AC pass status become unavailable; historical events remain readable.

A rejected `approve-intent` gate requires a changed spec digest, an operator-attested passing `validate-clarified-spec` check, and manual recovery before reapproval. Since the workflow writes `intent.md` after the gate, the later runner import must then show completed `record-intent` and successful `validate-intent` steps plus a runner snapshot containing an intent digest bound to the revised spec.

Runner and operator snapshots remain recordable during a spec revision even when the current manifest cannot yet validate against `intent.md`. The report then marks the manifest unavailable or stale. A passing verification is bound to the current spec digest; an older clarified-spec check cannot prove a revised spec.

Usage totals require complete, disjoint counters for every recorded route attempt and classifier invocation. A missing counter makes totals and dependent ratios unavailable. A `(stage, cause_id, attempt)` route observation must be unique; duplicate or contradictory observations invalidate the stream and cannot manufacture an underpowered signal. Rework spans begin with an evidenced reasoning failure, mechanical failure, or rejected attempt and end at an observed successful correction; only repeated distinct reasoning failures can form an underpowered signal.

A `pull_request` event records one Draft PR checkpoint (`draft_pr.py`, run by `run.py` at the end of every start or resume). Its source must be `runner`, and `ledger.py record` does not offer it. Fields: `outcome` (`pending`, `created`, `reused`, `failed-retryable`, `blocked-ambiguous`, `blocked-closed` or `blocked-unlinked`), optional `reason` (a fixed code allowed for that outcome, `PR_REASONS` in `ledger.py`), `issue` (int), `pr_number` (int), `pr_url` and `matches` (int, the matching PR count for `blocked-ambiguous` and `blocked-closed`). `pr_url` uses the `url` type, which accepts only `https://github.com/OWNER/NAME/pull/N`. `created` and `reused` require `pr_number` and `pr_url`; every other outcome requires `reason`. No field holds a branch name, remedy or other text; those appear only in the printed line. A `pull_request` event may follow any other event. The run report adds `pull_request`: the latest event's `data` plus its `observed_at`, or `{"available": false, "reason": "no checkpoint recorded"}`; the text report adds one `pull_request:` line, and aggregate reports are unchanged. The kind is additive and `schema_version` stays 1: earlier streams remain valid, while a stream containing `pull_request` is rejected by an older pinned Ballast, as with any unknown kind.

A `branch_sync` event records one branch synchronization check (`branch_sync.py`, run by `run.py` before the first agent step of every start, resume and continue). Its source must be `runner`, and `ledger.py record` does not offer it. Fields: `outcome` (`up-to-date`, `synchronized` or `blocked`), `cause` (one of `busy`, `git-unavailable`, `in-progress`, `wrong-branch`, `unknown-base`, `fetch-failed`, `not-feature-branch`, `diverged`, `dirty`, `conflict`, `push-failed`, `protected-input`, `internal-error`), `base_ref`, `base_before`, `base_after`, `head_before`, `head_after`, and the booleans `pushed`, `fast_forwarded`, `recovered`, `retryable`, `stale_plan` and `stale_review`, `recovered_from` (a run ID) and `overlap` (int). `base_ref` uses the `ref` type: 1–200 characters of `[A-Za-z0-9._/-]`, not starting with `-` or `/`, without `..`, `//` or `@{`, and not ending in `.lock` or `/`. Commits use the `oid` type: 40 or 64 lowercase hex characters. `blocked` requires `cause`; `up-to-date` and `synchronized` forbid it and require `base_ref`, `base_after`, `head_before` and `head_after`; `synchronized` also requires `pushed`. `retryable` applies only to `push-failed`, `recovered` only to `synchronized`, and `recovered_from` only with `recovered` true. No field holds a path, remedy, Git output or other text; the base name is the only name recorded. A blocked `continue` records its event in the source run's stream; a stream holding only one `branch_sync` event (a start blocked before its first step) is valid. When a synchronization changed files that the feature's plan or review evidence also covers, the overlapping paths (at most 200, with `truncated`) go to `branch-sync/stale/<key>/<event_id>.json` in the operator state directory, keyed by feature, with the event ID, run ID, feature, `observed_at`, the base reference and commits and the stale evidence kinds; `overlap`, `stale_plan` and `stale_review` may also appear on a blocked `protected-input`, which keeps the synchronization. The Draft PR section lists the feature's newest 20 such records. A `branch_sync` event may follow any other event. The run report adds `branch_sync`: the latest event's `data` plus its `observed_at`, or `{"available": false, "reason": "no check recorded"}`; the text report adds one `branch_sync:` line, and aggregate reports are unchanged. The kind is additive and `schema_version` stays 1: a stream containing `branch_sync` is rejected by an older pinned Ballast, as with any unknown kind.

An `acceptance_packet` event records one acceptance-packet step of the Draft PR checkpoint (`packet.py`, called by `draft_pr.py` after the `pull_request` event). Its source must be `runner`, and `ledger.py record` does not offer it. Fields: `outcome` (`published`, `updated`, `unchanged`, `pending` or `failed-retryable`), optional `reason` (a fixed code allowed for that outcome, `PACKET_REASONS` in `ledger.py`), `pr_number` (int), `head`, `base` and `feature_version` (`oid`), `packet_digest` (`sha`, the SHA-256 of the packet text without its `Generated:` line), `shortened` (bool) and the criterion counts `verified`, `failed`, `not_run`, `stale` and `missing` (int). `published`, `updated` and `unchanged` require `pr_number`, `head`, `base`, `feature_version`, `packet_digest` and all five counts; `pending` and `failed-retryable` require `reason` and keep `head` and `base` when known. No field holds text; remedies and exception types appear only in the printed line. The event may follow any other event. The run report adds `acceptance_packet`: the latest event's `data` plus its `observed_at`, or `{"available": false, "reason": "no packet recorded"}`; the text report adds one `acceptance_packet:` line, and aggregate reports are unchanged. The kind is additive and `schema_version` stays 1: earlier streams remain valid, while a stream containing `acceptance_packet` is rejected by an older pinned Ballast, as with any unknown kind.

The `oid` value type is a Git object ID: 40 or 64 lowercase hexadecimal characters. `verification` has an optional `commit` (`oid`): `ledger check` sets it to `HEAD`'s ID only when the checkout's implementation fingerprint equals `commit_tree(HEAD)`, meaning the checked code is exactly that commit's; a dirty checkout omits it, and events without it stay valid.

The implementation fingerprint (`implementation_tree`, the `snapshot` and `tree` fields) is the SHA-256 of a Git tree ID built in a private index: seeded with `read-tree HEAD` when `HEAD` exists, then `add -A -- . :!specs`, then `specs` removed. Seeding from `HEAD` makes tracked files matched by an ignore rule count, so a clean checkout's fingerprint equals `commit_tree(root, HEAD)`, which builds the same tree from a commit's objects alone (`read-tree <commit>`, `specs` removed, `write-tree`) without touching the worktree or the user's index. Both run Git with hooks and fsmonitor disabled. Upgrade note: snapshots recorded before this change do not match a re-snapshot of the same tree, so per-criterion checks, review and convergence events bound to them read stale once; re-run `ledger check` for each criterion and the affected reviews or convergence.

Acceptance-criterion IDs are read by `spec_criteria`: top-level list items `- **AC-NNN**:` and `N. **AC-NNN**:`, in document order, first occurrence only, each with a title (the text before `**When**`, without bold markers, at most 120 characters) and its 1-based line.

The archive also keeps the workflow definition, parsed default routing-policy rows with a digest, and validated AC manifests under `manifests/<sha256>.json`. `acceptance-evidence.json` in a feature directory maps every approved `AC-NNN` to named `unittest` methods; the tracked manifest is a definition, never test results or ledger data. A revised valid mapping creates another immutable archive version. The latest snapshot selects the current version, and checks tied to older versions become stale. `./scripts/check` and `./scripts/verify` are suite-wide verification only. An individual AC passes only when all mapped methods pass for the same implementation snapshot and manifest version. Reports label absent or unreliable evidence unavailable rather than inventing values.

Use `.ballast/spec_workflow/ledger.py import RUN_ID`, `record RUN_ID KIND --source SOURCE --data JSON`, `snapshot RUN_ID`, and `check RUN_ID AC-NNN tests.test_module.TestCase.test_method` for local recording. Use `./scripts/agent-metrics --run RUN_ID`, `./scripts/agent-metrics specs/N-slug`, or `./scripts/agent-metrics --all` for reports; add `--json` for machine-readable output. A corrupt stream produces diagnostics and a nonzero exit. The tool does not invoke a model or change routing defaults.
